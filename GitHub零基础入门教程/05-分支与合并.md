# 05 · 分支与合并（学会"开分身"）

> 分支是 Git 最强大、也最让小白犯怵的功能。但只要抓住一个比喻——**分支 = 平行宇宙 / 游戏存档分线**——就一点都不难。
> 这一章讲：为什么要用分支、怎么开/切/合分支、以及小白最怕的"**冲突**"到底怎么手把手解决。

---

## 一、为什么需要分支？

设想：你的项目 `main`（主线）是**线上正在用的、不能出错的**版本。现在你要开发一个新功能"用户登录"，要改好几天。问题来了：

- 直接在 `main` 上改？改到一半是个半成品，万一这时候要紧急修个别的 bug，整个项目都是乱的。
- 不改又没法开发。

**解法：从 `main` 岔出一条新分支 `login`，在分身里安心开发**。主线 `main` 始终保持干净可用。功能做完测好了，再把 `login` **合并**回 `main`。

```
                    ┌──● 写登录页 ──● 加密码校验 ──● 修小bug   (login 分支，你的分身宇宙)
                    │                                    │
 ●────●────●────────┴────────────────────────────────────┴──►●   (main 分支，主线)
 初始  改A   改B                                          合并回来
                  ↑                                       ↑
              从这里岔出去                            开发完，合并回主线
```

> 🔑 **核心好处**：
> 1. **隔离**：分支上随便折腾，搞砸了删掉就行，主线毫发无伤。
> 2. **并行**：好几个人各开各的分支，同时开发不同功能，互不干扰。
> 3. **可控**：功能在分支上做完、审查通过，才合并进主线，保证主线质量。
>
> 这就是为什么**真实团队几乎从不直接在 main 上改**，一切改动都先在分支上做。

## 二、分支的基本操作

### 看当前有哪些分支

```bash
git branch
```

```
* main      ← 星号表示你"现在站在" main 分支上
```

### 创建并切换到新分支（最常用）

```bash
git switch -c login
```

- `switch -c` = "创建（create）一个叫 `login` 的新分支，并立刻切换过去"。
- 切过去后，你的所有 commit 都记在 `login` 上，`main` 纹丝不动。

> 📌 你可能在老教程见到 `git checkout -b login`，作用完全一样。新版 Git 推荐用语义更清晰的 `git switch`（切分支）和 `git restore`（撤销改动），把老 `checkout` 一个命令干两件事拆开了。两种写法都能用。

### 在分支上正常干活

和第 4 章完全一样：改文件 → `add` → `commit`。比如：

```bash
echo "登录功能开发中" > login.md
git add .
git commit -m "新增登录功能初稿"
```

此时 `login` 比 `main` 多了一个提交。

### 切回主线看看

```bash
git switch main
```

你会发现 `login.md` **不见了**！别慌——它好好地待在 `login` 分支里。你现在站在 `main` 这个"宇宙"，自然看不到另一个宇宙的东西。再 `git switch login` 切回去，它又回来了。

> 💡 这正是分支的魔力：**同一个文件夹，切换分支就像切换平行宇宙**，眼前的文件会随之变成那个分支的样子。

## 三、合并分支：`git merge`

`login` 功能开发完、测试好了，要把成果合并回主线 `main`。

**记住合并的方向**：先站到"**要接收成果的**"分支（这里是 `main`），再把"**带来成果的**"分支（`login`）合并进来。

```bash
git switch main          # ① 先回到主线
git merge login          # ② 把 login 的成果合并进 main
```

合并成功后，`main` 上就有了 `login.md` 和登录功能的所有提交。

合并完，`login` 分支已经"功成身退"，可以删掉保持整洁：

```bash
git branch -d login      # 删除本地的 login 分支
```

> 别怕删分支：合并后它的提交已经进了 `main`，删的只是那个"标签指针"，历史不会丢。

## 四、重点来了：合并冲突（Conflict）怎么办

**什么时候会冲突？** 当**两个分支改了同一个文件的同一处**，Git 不知道该听谁的，就"罢工"让你来定夺。这是新手最慌的时刻，但其实**一点都不可怕**，跟着做：

### 制造一个冲突来演示

假设 `main` 和 `feature` 两个分支，都改了 `README.md` 的**同一行**：

- `main` 里这行是：`项目状态：稳定`
- `feature` 里这行被改成：`项目状态：开发中`

当你 `git merge feature` 时，Git 会报：

```
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
```

> 📌 **看到 CONFLICT 别慌**，Git 已经清楚告诉你：哪个文件冲突了（README.md），下一步该干嘛（解决冲突后提交）。

### 打开冲突文件，你会看到"奇怪的符号"

用编辑器打开 `README.md`，冲突的地方会被 Git 标记成这样：

```
<<<<<<< HEAD
项目状态：稳定
=======
项目状态：开发中
>>>>>>> feature
```

翻译一下这些符号：

| 符号 | 含义 |
| --- | --- |
| `<<<<<<< HEAD` | 从这里开始，是**当前分支（main）** 的版本 |
| `=======` | 分隔线，上面是我方、下面是对方 |
| `>>>>>>> feature` | 到这里结束，中间是**要合并进来的分支（feature）** 的版本 |

### 怎么解决？三步

**第 1 步：你来决定最终留什么**。手动编辑这段，把那些 `<<<`、`===`、`>>>` 符号**统统删掉**，只留你想要的最终内容。比如你决定融合两者：

```
项目状态：开发中（即将稳定）
```

> ⚠️ **务必把三行标记符号（`<<<<<<<`、`=======`、`>>>>>>>`）全部删干净**，一个都不能留，否则它们会变成文件里的垃圾文本。

**第 2 步：告诉 Git "这个文件我搞定了"**：

```bash
git add README.md
```

**第 3 步：完成这次合并提交**：

```bash
git commit -m "合并 feature，解决 README 冲突"
```

✅ 冲突解决完毕！是不是没想象中可怕？**解决冲突的本质就是：你这个"人类裁判"来决定有歧义的地方该听谁的，然后删掉标记、add、commit。**

### 解决冲突心法

1. **冲突是正常的**，不是你做错了什么，多人改同一处必然发生。
2. **不确定该留谁的，先去问改了对方那行的人**，别擅自删掉别人的工作。
3. 想放弃这次合并、回到合并前的状态：`git merge --abort`，一切复原，重头再来。
4. 平时勤 `git pull`、把任务拆小、别让一个分支拖太久，能大幅减少冲突。

## 五、分支操作命令小结

```bash
git branch                 # 查看所有分支
git switch -c <名字>       # 创建并切换到新分支
git switch <名字>          # 切换到已有分支
git merge <名字>           # 把指定分支合并进【当前】分支
git branch -d <名字>       # 删除分支
git merge --abort          # 合并出问题时，放弃合并、恢复原状
```

把改好的分支推到 GitHub（让别人也能看到）：

```bash
git push -u origin <分支名>
```
