# A 组 · 用 GitHub 管理"文字与知识"（专题 1–3）

> Git 最初为代码而生，但它管**任何会反复修改的文字**都极好用——论文、笔记、小说。本组三个专题教你把 Git 变成"写作者的时光机"。

---

## 专题 1 · 📄 用 GitHub 管理学术论文与写作

**适合谁**：学生、研究者、任何要反复改稿/投稿的人。

**为什么用 GitHub（解决你的真实痛点）**：
- 告别 `论文_最终版_真的最终_导师改.docx` 的混乱（[第 01 章](../01-Git和GitHub是什么.md) 那个经典烦恼）。
- 每次改动都有记录，**导师让你"改回上周那版"，一键就行**。
- 投稿不同期刊要不同版本？**用分支**各管一个，互不干扰。
- 云端备份，**电脑炸了论文还在**。

**怎么一步步做**：

1. **建仓库** `my-thesis`，选 **Private**（论文通常不公开）。
2. **组织结构**：
   ```
   my-thesis/
   ├── README.md          ← 写明论文题目、进度、待办
   ├── 正文/
   │   ├── 01-引言.md
   │   ├── 02-方法.md
   │   └── 03-结果.md
   ├── 图表/
   └── 参考文献.md
   ```
   > 💡 用 **Markdown 写**最适合 Git（纯文本，diff 清晰）。如果必须用 Word，Git 也能管 `.docx`，只是看不了逐行差异（看不到具体改了哪句，只知道文件变了）。
3. **每写一段就提交**：`完成引言初稿`、`按导师意见修改方法部分`——提交信息就是你的改稿日志。
4. **应对"投不同期刊"**：
   ```bash
   git switch -c 投稿-期刊A     # 为期刊A的格式要求开一个分支
   # ……按期刊A要求调整……
   git switch -c 投稿-期刊B     # 从主线再开一个给期刊B
   ```
   主线 `main` 保持你的"标准版"，各分支适配各期刊。
5. **追踪导师的修改**：导师返回修改后，你提交一版 `导师第3轮意见`，用 [diff](../25-必学模型/01-数据模型.md) 一眼看出他动了哪里。

**进阶点子**：
- 配合 **GitHub Pages**（[第 09 章](../09-用GitHub-Pages免费建网站.md)）把论文进度做成私人网页。
- 写作用支持 Git 的工具（如 Typora、Obsidian + Git 插件、VS Code）更顺手。
- 大的图表/数据文件用 `.gitignore` 排除或放别处，别撑大仓库（[避坑 15](../22-新手避坑指南.md)）。

> 🔑 核心收获：**把"另存为大法"换成"提交 + 分支"**，你的写作从此有了完整可追溯的历史和多版本管理能力。

## 专题 2 · 📚 用 GitHub 建一个长期知识库

**适合谁**：所有爱学习、爱整理的人。**你正在读的这套教程，本身就是这样一个知识库。**

**为什么用 GitHub**：
- 分门别类、长期积累，**越用越值钱**。
- README 当**导航目录**，点链接直达各篇（[第 21 章](../21-完整实战项目-从0搭建笔记库并发布成网页.md) 演示过）。
- 随时随地访问，还能发布成网页分享。

**怎么一步步做**：

1. 建仓库 `my-knowledge-base`（想公开分享选 Public，私人选 Private）。
2. **按主题分文件夹**，每个主题一个文件夹、内含编号文件（就像本仓库的"土壤宏基因组学"和"GitHub 教程"）：
   ```
   my-knowledge-base/
   ├── README.md          ← 总导航：列出所有主题 + 链接
   ├── 编程/
   │   ├── README.md      ← 本主题的子导航
   │   ├── 01-Python基础.md
   │   └── 02-Git笔记.md
   ├── 历史/
   └── 健康/
   ```
3. **README 做成地图**：用 Markdown 表格 + 链接列出所有主题（[第 10 章进阶语法](../10-美化主页与Markdown进阶.md)）：
   ```markdown
   | 主题 | 简介 | 入口 |
   | --- | --- | --- |
   | 💻 编程 | Python、Git 学习笔记 | [进入](./编程/README.md) |
   | 📜 历史 | 读史笔记 | [进入](./历史/README.md) |
   ```
4. **持续提交**：每学到新东西，加一篇或改一篇，commit 一次。

**进阶点子**：
- 用 **Mermaid** 画知识地图（[第 10 章](../10-美化主页与Markdown进阶.md)）。
- 发布成 **Pages 网页**，变成你的公开"第二大脑"。
- 用 **Issues** 记"想学但还没学"的清单（呼应专题 5）。

> 🔑 核心收获：一个**结构化、可检索、永久备份、能分享**的个人知识库，是复利最高的长期资产。

## 专题 3 · ✍️ 用 GitHub 写小说 / 剧本

**适合谁**：网文作者、编剧、任何长篇创作者。

**为什么用 GitHub（创作者的独特玩法）**：
- **用分支同时探索不同剧情走向/结局**，不用"另存好几个文件"。
- 删改了大段又后悔？历史里都在，随时找回（[撤销模型](../25-必学模型/02-操作模型.md)）。
- 用 **tag** 标记"第一稿定稿""出版版"等里程碑。

**怎么一步步做**：

1. 建仓库 `my-novel`（连载中通常 Private）。
2. **结构**：
   ```
   my-novel/
   ├── README.md        ← 设定、大纲、人物表
   ├── 设定/
   │   └── 人物小传.md
   └── 正文/
       ├── 第01章.md
       └── 第02章.md
   ```
3. **日常写作**：写完一章 `完成第5章：主角的抉择`，提交。
4. **探索不同结局**（杀手锏）：
   ```bash
   git switch -c 结局A-悲剧      # 在这个分支把故事写成悲剧
   git switch main
   git switch -c 结局B-圆满      # 从主线再开一个写圆满结局
   ```
   两个结局**并行存在、互不影响**，最后选定哪个再合并回 main。
5. **标记定稿**：第一稿写完，打个 tag：
   ```bash
   git tag -a v1.0-初稿 -m "全文初稿完成"
   git push origin v1.0-初稿
   ```
   以后无论怎么改，这个"初稿快照"永远能调出来。

**进阶点子**：
- 用 Issue 管理"待填的坑""要修的设定 bug"。
- 邀请编辑当 Collaborator，用 PR + 评论的方式提修改意见（像代码审查，但审的是文稿）。

> 🔑 核心收获：**分支让"如果这样写会怎样"变成可以安全探索的实验**，这是传统写作工具给不了的自由。

## ✅ A 组小结

| 专题 | 最大价值 | 关键 Git 用法 |
| --- | --- | --- |
| 论文写作 | 多版本 + 改稿可追溯 | 分支（多期刊）、diff（看改动） |
| 知识库 | 长期复利资产 | 文件组织、README 导航、Pages |
| 小说创作 | 安全探索不同走向 | 分支（不同结局）、tag（定稿） |

> 共同点：**它们管的都是"会反复改的文字"，而这正是 Git 的主场。** 把写作交给 Git，你就拥有了时光机和平行宇宙。
