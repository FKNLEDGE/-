# C 组 · 用 GitHub "团队协作与开源"（专题 8–10）

> 前两组多是"一个人玩"。这组带你进入**多人世界**——团队开发、开源贡献、跨设备同步。这也是 GitHub 最有威力的地方。

---

## 专题 8 · 👥 多人协作开发一个小网站（走一遍真实团队工作流）

**适合谁**：想练职场/团队技能的人。拉 1–2 个同学/朋友一起做最好。

**为什么用 GitHub**：这是**模拟真实公司开发**的最佳练习——分工、分支、PR、审查、合并，一个都不少。

**怎么一步步做（完整工作流）**：

1. **建仓库 + 加人**：一人建仓库 `team-website`，**Settings → Collaborators** 把队友加进来（[第 06 章](../06-团队协作-Fork与PR.md)）。
2. **约定工作流**：用最简单的 **GitHub Flow**（[模型 16](../25-必学模型/03-协作工程模型.md)）——**谁都不直接推 main，所有改动走分支 + PR**。
3. **分工开分支**：
   ```bash
   # A 同学做首页
   git switch -c feature/homepage
   # B 同学做关于页
   git switch -c feature/about-page
   ```
   两人**并行开发，互不干扰**（[分支隔离模型](../25-必学模型/02-操作模型.md)）。
4. **各自干活 + 发 PR**：
   ```bash
   git add . && git commit -m "完成首页布局"
   git push -u origin feature/homepage
   ```
   到 GitHub 发起 Pull Request。
5. **互相审查（关键！）**：队友在你 PR 的 **Files changed** 里逐行看、提意见（[代码审查模型](../25-必学模型/03-协作工程模型.md)）。改完继续在同分支提交，PR 自动更新。
6. **合并 + 同步**：审查通过点 **Merge**。**每个人合并后，其他人记得 `git switch main` + `git pull`** 同步最新（[同步优先框架](../26-思维框架.md)）。
7. **故意制造一次冲突**：让两人都改 `README.md` 同一行再合并，亲历团队里冲突怎么产生和化解（[第 05 章](../05-分支与合并.md)）。

**进阶点子**：
- 用 **Issues** 拆任务、分配给人（Assignees）。
- 配一个 [Actions](../12-GitHub-Actions自动化入门.md)，PR 自动检查，红了不让合。
- 用 **Projects 看板**看谁在做什么。

> 🔑 核心收获：你会**真正理解公司里代码是怎么协作出来的**——这套流程面试常问、入职就用。

## 专题 9 · 🎁 开源贡献的完整旅程（从找项目到 PR 被合并）

**适合谁**：想参与开源、给简历加分、和全球开发者协作的人。

**为什么用 GitHub**：开源几乎都在 GitHub。**你的 PR 被知名项目合并，是实打实的履历。**

**怎么一步步做（完整旅程）**：

**第一站 · 找一个适合新手的项目**
- 练手专用：搜 **`first-contributions`**（专门教新人提 PR 的项目，README 手把手）。
- 找真实任务：在项目的 Issues 里筛选标签 **`good first issue`**（维护者专门标给新人的简单任务）。
- 挑活跃的：看最近提交时间、Star、维护者是否回复（[第 15 章判断项目](../15-看懂和运行别人的项目.md)）。

**第二站 · 读懂项目**
- 先读 README 和 **CONTRIBUTING.md**（贡献指南，告诉你它的规矩）。
- 把项目 Clone 下来跑起来，理解它干嘛（[第 15 章](../15-看懂和运行别人的项目.md)）。

**第三站 · 动手贡献**（[Fork-PR 模型](../25-必学模型/03-协作工程模型.md)）
```
1. Fork 到你账号
2. git clone 你的 Fork
3. git switch -c fix-xxx        开分支
4. 改代码 / 修文档 / 补测试
5. git commit -m "清楚的说明"
6. git push -u origin fix-xxx
7. 到 GitHub 发起 Pull Request，说明你解决了什么（关联 Issue 写 Closes #xx）
```

**第四站 · 配合审查、直到合并**
- 维护者可能提意见，**别玻璃心**，按意见在同分支继续改、push，PR 自动更新。
- 被合并 🎉 你就是这个项目的 **Contributor** 了！
- 被婉拒也正常，礼貌道谢，换个项目再来。

**礼仪提醒**：
- 改动前最好先在 Issue 里说一声"我想做这个"，避免和别人撞车或做无用功。
- 遵守项目的代码风格和提交规范。
- 用英语沟通时简洁礼貌（[第 18 章缩写](../18-英文界面与报错直译对照.md)：LGTM/PTAL/nit）。

> 🔑 核心收获：从"开源的使用者"变成"贡献者"，这一步跨过去，你就真正进入了全球协作的世界。

## 专题 10 · 💾 用 GitHub 备份同步你的配置（dotfiles）

**适合谁**：爱折腾电脑、常换设备、想"换电脑一键还原"的人（偏进阶但很实用）。

**为什么用 GitHub**：
- 你精心调过的软件配置（编辑器设置、终端配置、快捷键等），**换台电脑就全没了**。
- 用 Git 管起来，**新电脑 clone 一下就全回来**，还自带历史（改坏了能回退）。

**怎么一步步做**：

1. 建仓库 `dotfiles`（这是社区约定俗成的名字）。
2. 把你想备份的配置文件放进去，比如：
   - VS Code 的 `settings.json`
   - 终端/Shell 的配置（如 `.bashrc`、`.zshrc`）
   - Git 自己的配置 `.gitconfig`
   ```
   dotfiles/
   ├── README.md          ← 说明每个文件是啥、怎么用
   ├── vscode-settings.json
   ├── .gitconfig
   └── .bashrc
   ```
3. **改了配置就提交**：`更新VS Code字体设置`，push 上去。
4. **换新电脑时**：`git clone` 下来，把这些文件放回对应位置（或用脚本/软链接自动放置）。

**进阶点子**：
- 写个简单的"安装脚本"把配置自动软链接到正确位置（搜 `dotfiles 管理` 有很多方案）。
- ⚠️ **绝不要把含密钥/密码/token 的配置传上去**（尤其 Public 仓库）！用 `.gitignore` 排除，或仓库设 Private（[避坑 1](../22-新手避坑指南.md)）。

> 🔑 核心收获：你的"数字工作环境"从此**可版本化、可备份、可一键迁移**——这是很多老程序员的必备习惯。
