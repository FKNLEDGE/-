# 26 · 7 个思维框架（装上"思维操作系统"再用 Git）

> 模型是"零件知识"，**思维框架是"遇事怎么想"**。同样会几条命令，会不会这 7 个框架，决定了你是"照葫芦画瓢、一出错就懵"，还是"心里有底、自己能推"。
> 每个框架给你一个**随时能套用的提问/动作**。建议读完贴在心里，操作前过一遍。

---

## 框架 1 · 三区域定位法："我这个改动，现在在哪一层？"

**核心**：任何时候，你的改动一定处在四层之一——**工作区 / 暂存区 / 本地仓库 / 远程**。遇事先问"它在哪层"，就知道下一步该用什么命令。

**怎么用**：
```
改了还没 add        → 在【工作区】    撤销用 git restore
add 了还没 commit   → 在【暂存区】    撤回用 git restore --staged
commit 了还没 push  → 在【本地仓库】  改用 amend / reset
push 了             → 在【远程】      只能用 revert 来更正
```

> 🔑 **小白最大的混乱来自"不知道东西在哪"。** 养成习惯：操作前先 `git status`（它会明确告诉你每个文件在哪层），再决定动作。**90% 的"我该敲啥"都能这样推出来。**

---

## 框架 2 · 快照-指针还原法："Git 内部其实只是在挪指针、加快照"

**核心**：任何看起来"神奇/可怕"的操作，都能还原成两件小事——**加一张快照**，或**移动一个指针**（模型 1、5）。这么一想，恐惧就没了。

**怎么用**（把吓人的操作翻译成"挪指针"）：
| 看起来吓人的 | 其实只是 |
| --- | --- |
| 开一个新分支 | 新建一个指向当前提交的指针（41 字节） |
| 切换分支 | 把 HEAD 指针指过去，工作区换成那张快照 |
| 合并 | 加一个有两个父亲的新快照 |
| reset 回退 | 把分支指针往回挪到某张旧快照 |
| 删分支 | 删掉一个指针（快照还在） |

> 🔑 当你不再把分支想成"复制整个项目"，而是"一张便利贴指针"，你就**敢开分支、敢切换、敢删**了——因为你知道底层啥也没搞坏。

---

## 框架 3 · 可逆性优先法："这步能撤销吗？怎么撤？"

**核心**：操作前先评估**可逆性**，并想好退路。Git 里绝大多数操作可逆（第一性原理 8），但**可逆程度不同**，越往"公开"走越难收回。

**怎么用**（一个可逆性光谱）：
```
易撤销 ◄─────────────────────────────────► 难撤销
restore   commit   reset(本地)   push   force-push   删库/泄密
(随便)    (amend)   (reflog兜底)  (revert) (危险)     (可能不可逆)
```

操作前自问三连：
1. 这步可逆吗？
2. 如果错了，用什么撤？（restore / reset / revert / reflog）
3. 它会不会**影响到别人**（已公开）？影响别人的就要格外谨慎。

> 🔑 推论：**对自己没 push 的东西大胆试，对已 push/会影响别人的东西三思**。带 🚨 的（强推、删库、改公开历史、传密钥）操作前必停一秒。

---

## 框架 4 · 提交即叙事法："让历史成为一篇能读的故事"

**核心**：提交历史不是给机器看的流水账，而是**写给未来的人（包括你自己）的故事**。好的历史，光看一行行 commit message 就能读懂"这个项目是怎么长成今天的"。

**怎么用**（一个好提交的三条标准）：
1. **原子性**：一个 commit 只做"一件完整的事"。别把"修 bug + 改样式 + 加功能"塞进一个提交。
2. **可读说明**：message 说清"做了什么"（必要时说"为什么"）。`修复登录在 Safari 下失效` ✅；`fix` ❌。
3. **能独立回退**：因为每个提交是一件独立的事，将来想单独撤掉其中一件才做得到。

> 🔑 检验法：假装三个月后的你来翻这段历史。你能看懂每一步在干嘛、为啥这么干吗？看不懂，就是提交拆得不好或说明写得烂。

---

## 框架 5 · 同步优先法："先对齐，再动手"

**核心**：分布式意味着"你的本地"和"远程/队友"随时可能不一致（模型 6、9）。协作里大量麻烦（push 被拒、大冲突）都源于"**基于过时的版本干活**"。

**怎么用**（一个雷打不动的节奏）：
```
开始干活 ──► 先 git pull（对齐到最新）──► 再改 ──► 小步 commit ──► push
                  ▲                                              │
                  └──────────── 频繁同步，别让分支拖太久 ◄────────┘
```

三条铁律：
1. **干活前先 pull**。
2. **任务拆小、分支短命**（拖越久，和主线差越远，冲突越大）。
3. **push 前再 pull 一次**，减少"被拒"。

> 🔑 冲突的根源往往不是"运气差"，而是"太久没同步"。同步优先，能把冲突扼杀在小处。

---

## 框架 6 · 隔离实验法："拿不准的，开个分支去试"

**核心**：主线（main）要随时可用（第一性原理 7）。所以**任何"拿不准、可能失败、做到一半"的工作，都不该直接在主线上做**，而要开个分支当沙盒。

**怎么用**（一个判断流程）：
```
我要做的这件事……
  ├─ 是"立刻完成、绝不会错"的小事吗？ → 极少数情况可直接在 main（个人项目）
  └─ 需要多步、可能反复、想让人审？   → 开分支！做完发 PR
                                         成了 merge，砸了删分支，main 全程干净
```

> 🔑 养成"**默认开分支**"的习惯。分支几乎零成本（框架 2），但能保护主线、隔离风险、方便审查。哪怕一个人的项目也这么练，把专业肌肉记忆养出来。

## 框架 7 · 信任与来源审视法："这段代码/这个改动，我凭什么信它？"

**核心**：开放协作意味着会接触**陌生人的代码**（别人的 PR、下载的项目、复制的命令）。不能盲目信任，也不能一概拒绝，而要**按来源评估风险**（第一性原理 9）。

**怎么用**（三个场景的审视清单）：
| 场景 | 问自己 |
| --- | --- |
| 收到陌生人的 PR | 改动我看懂了吗？有没有可疑操作？跑自动化测试过了吗？ |
| 下载/运行别人项目 | 来源可信吗（Star/活跃度）？安装脚本干了啥？要我填密钥/关杀毒的格外警惕 |
| 复制网上的命令 | 我看懂这条命令在干嘛吗？尤其带 `rm`、`--force`、`sudo`、`curl ... | sh` 的 |

> 🔑 一条朴素原则：**越是催你"快、别看、关掉安全软件"的，越要停下来。** 对自己的密钥/数据负责。详见 [第 15 章](./15-看懂和运行别人的项目.md)、[第 22 章避坑](./22-新手避坑指南.md)。

## 🧭 7 个框架速记卡（贴在心里）

```
1 三区域定位   ── 改动在哪层？→ 决定用什么命令
2 快照-指针    ── 再吓人的操作，也只是挪指针/加快照 → 别怕
3 可逆性优先   ── 这步能撤吗?怎么撤?会影响别人吗? → 再动手
4 提交即叙事   ── 一提交一件事 + 说清做了啥 → 历史可读
5 同步优先     ── 先 pull 对齐，再干活 → 少冲突
6 隔离实验     ── 拿不准就开分支 → 护住主线
7 来源审视     ── 这代码我凭啥信它? → 对安全负责
```

> 💡 **怎么练**：每次用 Git 卡壳或要做"大动作"时，翻出这张卡，挨个问一遍。用上十次八次，它们就内化成你的直觉了——到那时，你不是"会用 Git 的人"，而是"懂 Git 的人"。

## ✅ 本章自测

1. 你改乱了一个文件，想撤销——用框架 1，先判断它在哪层、该用哪条命令？
2. 你害怕"切换分支会不会把代码搞丢"——用框架 2 解释为什么不用怕。
3. 你要执行一个 `git reset --hard`，用框架 3 的"三连问"过一遍。
4. 你打算把"修 bug、改配色、加功能"一起提交，框架 4 会怎么建议你？
5. 团队里你总在 push 时被拒、还频繁冲突——用框架 5 找原因和对策。
