# 06 · 团队协作：Fork、Pull Request 与 Issue

> 前面都是你一个人玩。这一章进入 GitHub 真正的灵魂——**协作**。
> 你将学会两种协作模式、看懂 **Pull Request（PR）** 这个开源世界的核心机制，并亲手给一个开源项目提交你的第一份贡献。

---

## 一、两种协作模式：选哪种取决于"你有没有写权限"

### 模式 A：团队内部协作（你是项目成员，有写权限）

公司同事、课题组、自己和小伙伴的项目——大家都是这个仓库的**协作者（Collaborator）**，都能直接 push。

> 怎么把人加进来：仓库 **Settings → Collaborators → Add people**，输对方 GitHub 用户名邀请即可。

**标准流程**（也叫"功能分支工作流"）：

```
① git pull                      （先同步最新的 main）
② git switch -c my-feature      （开自己的分支干活）
③ 改代码 → add → commit          （在分支上提交）
④ git push -u origin my-feature （把分支推到 GitHub）
⑤ 在 GitHub 上发起 Pull Request  （申请合并进 main）
⑥ 队友 Review（审查）→ 通过 → 合并
```

> 🔑 **重点：哪怕你有权限，也别直接往 `main` 推**。所有改动都走"分支 + PR + 审查"，这样每个改动都有人把关、有记录可查。这是专业团队的铁律。

### 模式 B：开源贡献（你对别人的项目没有写权限）

你想给一个不属于你的开源项目（比如某个很火的工具）改个 bug、加个功能。你显然不能直接 push 到人家的仓库。这时用 **Fork** 流程。

---

## 二、Fork 是什么？和 Clone 有什么区别

这是小白最容易搞混的一对：

| | Fork（复刻） | Clone（克隆） |
| --- | --- | --- |
| 做什么 | 把**别人的仓库**复制一份**到你自己的 GitHub 账号下** | 把某个仓库**下载到你本地电脑** |
| 在哪 | 云端 → 云端（GitHub 上点一下按钮） | 云端 → 本地（命令行 `git clone`） |
| 结果 | 你账号下多出一个一模一样的仓库，**你对它有完全权限** | 你电脑上多出一个项目文件夹 |
| 比喻 | 把别人的菜谱**抄一份到你自己的菜谱本** | 把菜谱**打印出来拿回家** |

```
   原作者的仓库                    你 Fork 之后
 github.com/作者/项目  ──Fork──►  github.com/你/项目   （你账号下的副本，你能随便改）
                                       │
                                    git clone
                                       ▼
                                  你的本地电脑
```

## 三、完整实战：给开源项目提交你的第一个 PR

这是本教程**含金量最高**的一节。假设你发现某开源项目 README 有个错别字，想帮忙改正。**七步走**：

### 第 1 步：Fork 到自己账号

打开那个项目主页，点右上角 **Fork** 按钮。稍等片刻，你的账号下就有了一个副本 `github.com/你的用户名/项目名`。

### 第 2 步：把你的 Fork 克隆到本地

```bash
git clone https://github.com/你的用户名/项目名.git
cd 项目名
```

### 第 3 步：开一个分支来改（养成好习惯）

```bash
git switch -c fix-typo
```

### 第 4 步：改东西，然后 add → commit

改正那个错别字，然后：

```bash
git add .
git commit -m "修正 README 中的拼写错误"
```

### 第 5 步：推到你的 Fork

```bash
git push -u origin fix-typo
```

### 第 6 步：发起 Pull Request（关键一步）

1. 打开你的 Fork 仓库页，GitHub 通常会贴心地弹出一个黄色横幅 **"Compare & pull request"**，点它。（没看到就点 **Pull requests 标签页 → New pull request**）
2. 你会进入一个对比页面，确认方向是：
   ```
   base: 原作者/项目 : main   ◄──  compare: 你/项目 : fix-typo
   （要合并进的目标）              （你的改动来源）
   ```
3. 填写 PR 的**标题**和**说明**：说清楚你改了什么、为什么改。比如：
   - 标题：`修正 README 拼写错误`
   - 说明：`第 3 段 "recieve" 应为 "receive"，本 PR 予以修正。`
4. 点 **Create pull request**。

🎉 **你的第一个 Pull Request 诞生了！** 它是一封正式的"请求"：嘿原作者，我在我的副本里做了这些修改，你看看要不要合并进你的项目？

### 第 7 步：等待 Review，配合修改

原作者会收到通知，他可能会：

- **直接 Merge（合并）** —— 你的修改进入了人家的项目，你正式成为**贡献者**！🎉
- **留 Review 评论** —— 提出修改意见。你只要在**本地同一个分支**继续改 → `add` → `commit` → `push`，**这些新提交会自动出现在同一个 PR 里**，不用重开 PR。
- **Close（关闭）** —— 觉得不需要，礼貌地谢过就好，这很正常。

> 🔑 **PR 的本质**：它不是"代码本身"，而是一个**围绕一组改动的讨论 + 审查 + 合并的场所**。能逐行评论、能讨论、能要求修改、能跑自动化测试，通过了才合并。这正是 GitHub 强大的核心。

## 四、Pull Request 页面里都有啥

一个 PR 页面通常有这几个标签，认一认：

| 标签 | 内容 |
| --- | --- |
| **Conversation** | 总讨论区：PR 说明、所有评论、状态（开放/已合并/已关闭） |
| **Commits** | 这个 PR 包含了哪几次提交 |
| **Files changed** | **逐行 diff**：绿色是新增、红色是删除。审查者在这里**对着某一行留评论** |
| **Checks** | 自动化检查（CI）的结果：测试过没过、代码规范合不合格 |

> 💡 **Code Review（代码审查）** 就发生在 "Files changed" 里：审查者把鼠标移到某行，点出现的 ➕，就能针对那一行提意见。这是团队保证质量、互相学习的关键环节。

## 五、Issue：项目的"留言板 / 工单系统"

**Issue（问题）** 是用来**讨论、报告、追踪**的地方，注意它**不直接改代码**。常见用途：

- 🐛 **报 Bug**：「我点登录按钮没反应，浏览器是 Chrome，步骤是……」
- 💡 **提需求/建议**：「希望增加深色模式」
- ❓ **提问 / 讨论**：「这个参数是干嘛的？」
- ✅ **任务追踪**：把要做的事拆成一个个 Issue，做完关闭

**怎么提一个好 Issue：**

1. 项目主页 → **Issues 标签 → New issue**。
2. **标题**精准：`登录按钮在 Safari 下点击无反应`，而不是 `有bug`。
3. **正文**写清楚：
   - 你想做什么、**期望**什么结果；
   - **实际**发生了什么；
   - **复现步骤**（怎么一步步触发的）；
   - 环境信息（系统、浏览器、版本）；
   - 截图 / 报错信息（直接把图拖进编辑框就能贴）。

> 🔗 **Issue 和 PR 的配合**：常见流程是"**先开 Issue 讨论 → 大家同意怎么改 → 提 PR 解决它**"。在 PR 说明里写上 `Closes #12`，当这个 PR 被合并时，**编号 12 的 Issue 会自动关闭**，非常方便。

## 六、其它你会遇到的协作名词

| 名词 | 一句话 |
| --- | --- |
| **Star ⭐** | 收藏/点赞项目。Star 多 = 受欢迎，也方便你以后在"Your stars"里找回来 |
| **Watch 👁** | 订阅项目动态，有新 Issue/PR 就通知你 |
| **Collaborator** | 被仓库主人加进来的、有写权限的协作者 |
| **Maintainer** | 项目维护者，负责审 PR、管方向的人 |
| **Contributor** | 贡献者，PR 被合并过的人就算（你提交一个 PR 被合并，就是了！） |
| **CI / Actions** | 自动化流程：每次提交自动跑测试、检查、部署。PR 里的 ✅/❌ 就是它 |
