# 01 · Git 和 GitHub 到底是什么（先搞懂"为什么"）

> 这一篇不教任何命令，只讲清楚一件事：**Git 和 GitHub 到底解决了你的什么烦恼。**
> 把这个想透了，后面的命令你都能"猜"出来为什么要存在。

---

## 一、先从一个你一定遇到过的烦恼说起

你写一篇论文 / 做一份 PPT，文件夹里大概长这样：

```
毕业论文.doc
毕业论文-修改版.doc
毕业论文-修改版2.doc
毕业论文-导师改过.doc
毕业论文-最终版.doc
毕业论文-最终版-真的最终.doc
毕业论文-最终版-打死不改了.doc
```

这套"另存为大法"有三个要命的问题：

1. **找不回历史**：你想看"三天前那一版怎么写的"，得靠文件名猜，猜错就没了。
2. **不知道改了啥**：`最终版` 和 `真的最终` 到底差在哪？只能两个文件并排一行行对。
3. **多人协作是灾难**：你发给导师，同时同学也在改，两份改完的文件**怎么合并回一份**？基本靠人肉复制粘贴，还容易覆盖掉别人的修改。

**这三个问题，就是"版本控制"这门技术要解决的全部。**

---

## 二、第一性原理：从基本事实推出 Git

我们用"基本事实 ➜ 必然后果 ➜ 于是诞生了什么"的方式，把 Git 推导出来。

### 事实 1：文件会不断被修改，而旧版本有时还需要找回来

**后果**：光存"当前这一版"不够，得把**每一次有意义的修改都存成一个快照**，并且能随时跳回任何一个快照。

**于是诞生了**：**版本控制（Version Control）**——一个自动帮你保存每一版、还能"时光倒流"的系统。Git 就是目前世界上最流行的版本控制工具。

> 🔑 一句话：**Git = 文件的"时光机 + 自动存档"。** 它记下你项目的每一个历史版本，让你随时能回到过去、对比差异。

### 事实 2：每次保存，你想知道"这次到底改了什么、谁改的、为什么改"

**后果**：每个存档点不能只是一坨文件，还得附带**说明信息**：什么时间、谁、改了哪几行、一句话说明为什么改。

**于是诞生了**：**提交（Commit）** 这个概念。一次 commit = 一个存档点 = 一张"快照"，上面贴着标签：作者、时间、一句话说明（commit message），以及"相比上一版，增删改了哪些行"。

```
提交历史（越往下越新）：
●  a1b2c3  "初始化论文框架"           —— 张三, 6月1日
●  d4e5f6  "补充第二章实验数据"        —— 张三, 6月3日
●  7g8h9i  "按导师意见修改结论"        —— 张三, 6月5日   ← 你现在在这里
```

想回到 6 月 3 日那版？一条命令的事，而且**完全不丢失**后面的版本。

### 事实 3：你想同时尝试好几个改法，又不想互相干扰

**后果**：需要一种机制，能从某个版本"岔开"出一条独立的线去试验，试成功了再合并回来，试失败了直接扔掉、主线毫发无伤。

**于是诞生了**：**分支（Branch）**。它就像游戏的"存档+读档"，或者平行宇宙——主线宇宙不动，你开个分身宇宙随便折腾。（第 5 章详讲）

## 三、那 GitHub 又是什么？Git 不够用吗？

到这里，**Git 已经能在你一台电脑上独立工作了**——不用联网、不用注册任何账号，它就是装在你电脑上的一个工具。

但它有两个天生的短板：

1. **只在你这一台电脑上**。电脑丢了 / 硬盘坏了，所有历史一起没。
2. **别人看不到、参与不进来**。你的 Git 仓库是你的私人时光机，同事怎么和你一起改？

**于是诞生了 GitHub**：

> 🔑 一句话：**GitHub = 一个放 Git 仓库的网站。** 它把你本地的 Git 仓库**搬一份到云端**，于是有了三大好处：
> 1. **备份**：代码在云上，电脑炸了也不怕。
> 2. **协作**：把网址发给别人，全世界都能来一起改（在你允许的前提下）。
> 3. **门面 / 社交**：每个项目有主页，能展示、能点赞（Star）、能讨论。程序员的 GitHub 主页约等于"作品集简历"。

### 一个比喻，彻底分清两者

| | 类比 | 说明 |
| --- | --- | --- |
| **Git** | 你电脑里的**单反相机** | 一个工具，负责"拍快照、存历史"。没网也能用，是它本身。 |
| **GitHub** | **网络相册 / 云盘**（如百度网盘、Google Photos） | 一个网站，负责把相机拍的照片传上去、备份、分享、让别人评论。 |

相机（Git）离了网络相册（GitHub）照样能拍照存档；网络相册离了相机就没照片可存。**它们是工具和平台的关系，不是一个东西。**

```
   Git（工具，装在你电脑里）              GitHub（网站，在云端）
 ┌──────────────────────┐             ┌─────────────────────┐
 │  拍快照、存历史、开分支  │  ── 上传 ──► │  备份、展示、协作、讨论 │
 │  （单机就能用）         │  ◄─ 下载 ──  │  （需要联网+账号）     │
 └──────────────────────┘             └─────────────────────┘
```

## 四、那 GitLab、Gitee（码云）又是什么？

它们和 GitHub 是**同类竞品**——都是"放 Git 仓库的网站"。Git 这个工具是统一的，但"云端平台"有好几家：

| 平台 | 一句话 | 适合谁 |
| --- | --- | --- |
| **GitHub** | 全球最大，开源项目几乎都在这；被微软收购 | 想接触全球开源、找资料、刷影响力 |
| **Gitee（码云）** | 国内平台，**访问速度快、界面中文**、不用翻墙 | 国内用户、网络不稳定、企业内部 |
| **GitLab** | 可以自己架在公司服务器上，企业自建首选 | 公司内部私有部署 |

> 💡 给国内小白的实话：GitHub 偶尔访问慢/不稳。**学习概念用本教程，练手时如果 GitHub 卡，可以先在 Gitee 上练**——操作几乎一模一样，因为底层都是同一个 Git。本教程以 GitHub 为例，但命令在哪家都通用。

## 五、几个你马上会反复听到的词（先混个脸熟，别背）

| 词 | 英文 | 一句话人话 | 比喻 |
| --- | --- | --- | --- |
| 仓库 | Repository / Repo | 一个被 Git 管理的"项目文件夹" | 一个项目的"档案柜" |
| 提交 | Commit | 一次存档（一张带说明的快照） | 游戏里按一次"保存" |
| 分支 | Branch | 从某个版本岔出去的一条独立线 | 平行宇宙 / 游戏存档分线 |
| 克隆 | Clone | 把云端仓库**完整下载**到本地 | 把云盘文件夹同步到电脑 |
| 推送 | Push | 把本地的提交**上传**到 GitHub | 上传到云盘 |
| 拉取 | Pull | 把 GitHub 上的更新**下载**到本地 | 从云盘下载最新 |
| 复刻 | Fork | 把**别人的**仓库**整个复制一份到你账号下** | 把别人的菜谱抄一份到自己本子 |
| 拉取请求 | Pull Request (PR) | "我改好了，请你把我的修改合并进去"的申请 | 给作者递交"修改建议书" |
| 问题 | Issue | 提 bug、提需求、讨论的帖子 | 项目的"留言板 / 工单" |
| 点星 | Star | 收藏/点赞一个项目 | 微博点赞 + 收藏 |

> 这些词在后面每一章都会**用具体例子**重新讲一遍，这里看不懂完全没关系，扫一眼就行。
