# 22 · 新手避坑指南（这些坑，提前知道就不会踩）

> 每个用 GitHub 的人都踩过坑。这一篇把小白**最常踩、最影响心情、甚至有点危险**的坑集中起来，告诉你**为什么会踩、怎么提前避开、踩了怎么救**。
> 读一遍混个眼熟，真遇到了回来查。带 🚨 的是"可能造成损失"的重要坑，重点看。

---

## 一、🚨 安全类（这几个可能造成真损失，最重要）

### 坑 1：把密码、密钥、Token 提交上去了

**怎么踩的**：项目里有个 `config.py`、`.env` 写着数据库密码或 API 密钥，`git add .` 一把全加了，push 上公开仓库。

**为什么严重**：①公开仓库**全世界可见**，有机器人专门扫 GitHub 上泄露的密钥；②**删文件没用**，它还在提交历史里。

**怎么避开**：
- push 前**永远先看一眼 `git status` / Desktop 的 Changes**，确认传的是啥。
- 敏感文件**第一时间写进 `.gitignore`**（第 04 章）。
- 用 `.env.example`（不含真实值的模板）代替真实的 `.env`。

**踩了怎么救**：
1. **立刻去把那个密钥/密码作废、重置**（当它已泄露），这是第一位的！
2. 再处理仓库（第 07 章"误传敏感文件"）。

> 🔑 记住：**作废密钥 > 删历史**。删了历史但没作废密钥，等于没救。

### 坑 2：误把仓库设成 Public，泄露了私人内容

**怎么踩的**：建仓库时手快选了 Public，把日记、工作资料、含隐私的东西传了上去。

**怎么避开**：建仓库时**看清 Public/Private**。拿不准就先选 **Private**，想公开随时能改。

**踩了怎么救**：Settings → Danger Zone → Change visibility 改回 Private。但**如果已经被人看到/下载/搜索引擎收录了，就来不及了**——所以事前看清最重要。

### 坑 3：在 Danger Zone 手抖删了仓库

**怎么避开**：仓库设置最底部的 **Danger Zone（危险区域）** 放着删库、改公开性等操作，**进去时手稳一点，看清再点**。删除要你输入仓库全名确认，别无脑复制粘贴。

**踩了怎么救**：90 天内可能能恢复（Settings 里找 Deleted repositories 或联系官方），但别指望。

## 二、命令行/终端类（最影响心情的低级坑）

### 坑 4：把命令前面的 `$` 也敲了进去

**现象**：报 `$: command not found`。

**为什么**：教程里 `$ git status` 的 `$` 是**提示符**，不是命令的一部分（第 00、16 章）。

**避开**：只敲 `$` 后面的内容。本教程代码块**不带 `$`**，放心复制。

### 坑 5：在错误的文件夹里敲 git 命令

**现象**：报 `fatal: not a git repository`。

**为什么**：你不在那个项目文件夹里（第 00 章）。

**避开**：敲 git 命令前先 `pwd` 看在哪、`ls` 看有没有 `.git`，或养成 `cd` 进项目再操作的习惯。Windows 可在项目文件夹右键 **Git Bash Here** 直接定位。

### 坑 6：`git commit` 后卡在一个全屏黑界面出不来（Vim）

**现象**：屏幕变成一个奇怪编辑器，敲字也不对，关不掉。

**为什么**：commit 忘了带 `-m "说明"`，弹出了 Vim 编辑器。

**逃生**：按 `Esc`，输入 `:q!`，回车。然后记得 commit 带上 `-m "说明"`（第 04、07 章）。

### 坑 7：复制了带格式的命令，引号变成"中文引号"

**现象**：命令报奇怪的错，肉眼看着没问题。

**为什么**：从某些网页/微信复制命令，英文引号 `"` 被自动变成了中文引号 `"` `"`，或空格变成了全角空格。

**避开**：命令里的引号**手动重敲一遍英文引号**；或从代码块（等宽字体那种）复制，别从正文复制。

## 三、提交习惯类（不致命，但拖累你和队友）

### 坑 8：提交信息写 `update`、`改改改`、`111`、`asdf`

**为什么是坑**：三个月后看历史，一排无意义信息，等于没记录。出问题想回退都不知道回哪。

**好习惯**：一句话说清**这次做了什么**。
- ❌ `update` / `改了一下` / `fix`
- ✅ `修复登录按钮点击无反应` / `补充第三章实验数据` / `更新读书清单，新增3本`

### 坑 9：攒一大堆改动，一次性提交

**为什么是坑**：一次 commit 改了 50 个文件、干了 5 件不相关的事，将来想回退其中一件做不到，审查也累。

**好习惯**：**小步快跑**，做完一件相对独立的事就提交一次。提交是免费的、本地的，多提交不要钱。

### 坑 10：几个月不 commit，全靠"另存为"

**为什么是坑**：那你等于没用 Git，又回到了 `最终版_真的最终.doc` 的老路。

**好习惯**：养成"改完一段就提交"的肌肉记忆。哪怕一天一次也好。

## 四、协作类（多人时容易踩）

### 坑 11：干活前不 pull，上来就改

**现象**：改完想 push，被拒 `Updates were rejected`，还可能撞一堆冲突。

**为什么**：别人已经更新了云端，你基于旧版本改，自然冲突。

**好习惯**：🔑 **每次开始干活前，先 `git pull`（或 Desktop 点 Fetch/Pull）**。先同步到最新再动手，能避免大量冲突。

### 坑 12：直接往 main 推，不走分支

**为什么是坑**：main 是大家共用的主线，你一个半成品推上去，可能搞乱所有人的工作。

**好习惯**：**任何改动先开分支，做完发 PR**（第 05、06 章）。哪怕一个人的项目也这么练，养成专业习惯。

### 坑 13：看到 `CONFLICT` 就慌了、乱删

**为什么是坑**：冲突时文件里有 `<<<<`/`====`/`>>>>` 标记，慌乱中可能把别人的代码整段删了。

**好习惯**：冲突很正常（第 05 章）。冷静看清"我的版本"和"对方的版本"，**不确定就去问改了那行的人**，别擅自丢掉别人的工作。真乱了用 `git merge --abort` 重来。

## 五、认知类（观念上的坑）

### 坑 14：以为 Git 和 GitHub 是一个东西

**纠正**：Git 是**工具**（装在你电脑上，没网也能用），GitHub 是**网站**（放 Git 仓库的云平台）。第 01 章用"相机 vs 网络相册"讲清了。

### 坑 15：往 Git 里塞大文件（视频、数据集、安装包）

**为什么是坑**：Git 适合管**文本**（代码、笔记）。塞几百兆的视频/数据，仓库会变得巨大、clone 巨慢，还可能超限被拒（单文件 >100MB 直接拒绝）。

**好习惯**：大文件用网盘/专门的存储；非要版本管理大文件用 Git LFS（小白一般用不到）。`.gitignore` 掉那些自动生成的大文件夹（`node_modules` 等）。

### 坑 16：以为提交了就等于传到 GitHub 了

**纠正**：`commit` 只是**存到本地**，`push` 才**上传到云端**（第 04 章三区域）。很多人 commit 完以为万事大吉，其实没 push，换台电脑就傻眼。**改完记得 push。**

### 坑 17：怕把东西弄丢、不敢操作

**纠正**：恰恰相反——**Git 极难真正丢东西**。`commit` 过的几乎都能用 `git reflog` 找回（第 07 章）。**大胆试、小心删**：只要养成多 commit 的习惯，你的每一步都有后悔药。

## 六、一张"提交前自检清单"（贴在心里）

每次 push 前，花 5 秒过一遍：

```
□ 我 pull 过最新了吗？（协作时）
□ git status / Changes 里，要传的文件对吗？有没有混进密码、大文件、垃圾文件？
□ 提交信息写清楚"做了什么"了吗？
□ 我是在分支上改的吗？（团队协作时）
```

> 🔑 **90% 的坑，都能被这 4 条自检挡在门外。**
