# 30 · 真实案例库（12 个真实场景：翻车、拯救与顿悟）

> 前面讲"该怎么做"，这一篇讲"**别人真实遇到了什么、怎么过来的**"。每个案例都是小白会真实撞上的场景，用"发生了什么 → 怎么处理 → 学到了什么"讲，帮你**在别人的经历里提前长记性**。
> 不用按顺序读，挑标题感兴趣的看。带 🚨 的是"教训值钱"的案例。

## 案例 1 · 🚨 把数据库密码 push 上了公开仓库

**发生了什么**：小王第一次做项目，`git add .` 一把梭，把写着数据库密码的 `config.py` 提交并 push 到了 Public 仓库。半小时后收到 GitHub 的安全警告邮件——有自动扫描机器人发现了密钥。

**怎么处理**：
1. **第一时间登录数据库后台，把那个密码改掉**（当它已经泄露，因为确实泄露了）。
2. 把 `config.py` 写进 `.gitignore`，并 `git rm --cached config.py` 后提交，让最新版不再含它。
3. 知道光这样历史里还有，但因为**密码已经改了，旧密码作废**，风险已解除。

**学到了什么**：
- 🔑 **泄密后第一动作永远是"作废密钥"，不是"删文件"**。删文件慢一步都没用，历史和别人的副本里可能都有。
- push 前 `git status` 看一眼传了啥；敏感文件提前进 `.gitignore`。
- 👉 对应 [避坑 1](./22-新手避坑指南.md)、[第 07 章](./07-常见问题与撤销操作.md)。

## 案例 2 · `git reset --hard` 之后，一上午的代码"没了"

**发生了什么**：小李想撤销一些改动，网上抄了条 `git reset --hard HEAD~3`，回车后傻眼——不仅撤销了提交，**一上午写的没提交的代码也全没了**，工作区被清空。

**怎么处理**：
1. 冷静，没关。敲 `git reflog`，看到了 reset 之前那一步的记录和它的哈希。
2. `git reset --hard <那个哈希>` 跳回去，提交回来了。
3. （但"从未 commit 过"的那部分改动确实找不回了——reflog 只能救"曾经 commit 过"的。）

**学到了什么**：
- 🔑 **`--hard` 会丢工作区改动，用前三思**；`git reflog` 是"曾经提交过的"终极后悔药。
- 推论：**多 commit 才有得救**。半天不提交，一旦误删就真没了。养成小步提交的习惯。
- 👉 对应 [撤销模型](./25-必学模型/02-操作模型.md)、[第 07 章场景 C](./07-常见问题与撤销操作.md)。

## 案例 3 · push 一直被拒，越搞越乱

**发生了什么**：小张在公司电脑改了代码，push 时报 `Updates were rejected`。他不懂，反复试、又加 `--force`，结果**把同事的提交覆盖没了**，同事炸了。

**怎么处理（正确姿势）**：
- 被拒只是因为**远程有你没有的更新**。正确做法是 `git pull` 拉下来合并（可能解决冲突），再 `git push`。**绝不该上来就 `--force`**。
- 同事的提交后来靠 `reflog` 和 GitHub 上的记录找了回来，虚惊一场。

**学到了什么**：
- 🔑 **`git push --force` 是核武器，会覆盖别人的工作，协作中几乎永远不要用裸 force**。真要强推也用更安全的 `--force-with-lease`。
- 看到 `rejected` 不要慌、不要 force，先 `pull`。
- 👉 对应 [推拉同步模型](./25-必学模型/02-操作模型.md)、[第 07 章报错 1](./07-常见问题与撤销操作.md)。

## 案例 4 · 一直在 main 上改，团队乱成一锅粥

**发生了什么**：三个同学合作做项目，图省事都直接往 main 推。结果天天冲突、互相覆盖，main 经常是跑不起来的半成品，谁也不敢拉最新。

**怎么处理**：
- 改用 **GitHub Flow**：约定**谁都不直接推 main**，每个改动开分支、发 PR、互相审查后再合并。
- main 从此始终保持"可用、经过把关"，冲突也大幅减少（都在小分支里早早解决了）。

**学到了什么**：
- 🔑 **专业团队几乎从不直接改主线**——不是规矩死板，是为了"主线随时可用"。
- 哪怕图省事，分支 + PR 长期看反而**更省事**（少了救火时间）。
- 👉 对应 [工作流模型](./25-必学模型/03-协作工程模型.md)、[隔离实验框架](./26-思维框架.md)、[专题 8](./27-专题实战/03-团队协作与开源.md)。

## 案例 5 · 提交历史全是"update"，出 bug 没法定位

**发生了什么**：小陈的项目出了个 bug，想看看是哪次改动引入的。翻开历史一看，一排 `update`、`改了下`、`111`、`fix`，**完全看不出每次干了啥**，只能一个个版本试，浪费一下午。

**怎么处理**：从此强制自己每次提交写清"做了什么"，比如 `修复用户名含空格时登录失败`。一个月后再遇到问题，扫一眼历史就定位到了。

**学到了什么**：
- 🔑 **commit message 是写给未来的你的**。当时省 5 秒，将来花几小时。
- 好习惯：一句话说清"做了什么"，必要时说"为什么"。
- 👉 对应 [提交即叙事框架](./26-思维框架.md)、[避坑 8](./22-新手避坑指南.md)。

## 案例 6 · 看到一堆 `<<<<<` 符号，以为仓库坏了

**发生了什么**：小刘第一次 pull 后,打开文件看到一堆 `<<<<<<< HEAD ... ======= ... >>>>>>>`，吓坏了，以为文件损坏，差点把整个项目删了重新 clone。

**怎么处理**：其实那只是**合并冲突标记**，Git 在喊他当裁判。他冷静下来，删掉标记、留下想要的内容、`add` + `commit`，冲突就解决了，啥也没坏。

**学到了什么**：
- 🔑 **冲突是设计，不是故障**。那些尖括号是 Git 在诚实地说"这里要你决定"。
- 别慌、别删项目。看不懂的报错先查，别做破坏性动作。
- 👉 对应 [冲突裁决模型](./25-必学模型/02-操作模型.md)、[第 05 章](./05-分支与合并.md)。

## 案例 7 · commit 了好几天，换电脑发现"什么都没有"

**发生了什么**：小赵在家电脑上认真写了三天、commit 了十几次，周一去公司 clone 项目准备继续，**发现一个都没有**——三天白干？

**怎么处理**：回家一看，本地这十几个 commit 都在，只是**从来没 push**。push 上去，公司就能拉到了。虚惊一场，但出了身冷汗。

**学到了什么**：
- 🔑 **commit 只到本地，push 才上云**（分布式的直接结果）。"提交了"不等于"传上去了"。
- 养成习惯：**每天收工前 push 一次**，让云端始终有最新备份。
- 👉 对应 [分布式模型](./25-必学模型/01-数据模型.md)、[避坑 16](./22-新手避坑指南.md)。

## 案例 8 · 误把仓库设成 Public，泄露了工作内容

**发生了什么**：小孙建公司项目仓库时手快选了 Public，含内部资料的代码公开了大半天才被发现。

**怎么处理**：立刻 Settings → Danger Zone 改回 Private。但因为已经公开过，不确定有没有被人看到/收录，只能向上汇报、评估影响。

**学到了什么**：
- 🔑 **建仓库时看清 Public/Private**。拿不准先选 Private，想公开随时能改；反过来"泄露了再补救"往往来不及。
- 公司/隐私内容默认私有。
- 👉 对应 [避坑 2](./22-新手避坑指南.md)、[第 14 章](./14-新手十万个为什么.md)。

## 案例 9 · 第一个开源 PR 被拒，差点不敢再提

**发生了什么**：小周鼓起勇气给一个开源项目提了 PR，结果维护者留了一堆修改意见，还有一条说"这个功能我们暂时不需要"。小周很受打击，觉得自己是不是太菜。

**怎么处理**：他冷静后发现，大部分意见是合理的代码风格建议。他按能改的改了，push 更新了 PR；那条"不需要的功能"礼貌回复表示理解。最终另一个小 PR 被合并了，他成了 Contributor。

**学到了什么**：
- 🔑 **审查是对代码不是对人**，被提意见、被拒太正常了，连资深开发者都天天经历。
- 从 `good first issue` 和改文档/错别字开始，更容易成功、建立信心。
- 👉 对应 [代码审查模型](./25-必学模型/03-协作工程模型.md)、[专题 9](./27-专题实战/03-团队协作与开源.md)。

## 案例 10 · 把 100 个文件一次性提交，回退时欲哭无泪

**发生了什么**：小吴攒了一周的改动，一次 `git add .` + commit，一个提交里混了"加新功能、改样式、修三个 bug、删旧代码"。后来发现其中一个改动有问题想单独撤掉——做不到，因为它和其他九件事**绑在同一个提交里**。

**怎么处理**：只能手动把那部分改回来再提交一次。从此他改成"做完一件相对独立的事就提交一次"。

**学到了什么**：
- 🔑 **一个 commit 只做一件事（原子性）**，将来才能单独回退、单独审查。
- 提交是免费的，多提交不要钱，别攒大包。
- 👉 对应 [提交即叙事框架](./26-思维框架.md)、[避坑 9](./22-新手避坑指南.md)。

## 案例 11 · 仓库越来越大，clone 要等十分钟

**发生了什么**：小郑往仓库里塞了一堆视频素材和几百兆的数据集，半年后仓库好几个 G，同事每次 clone 要等十几分钟，还有人因为单个文件超 100MB 被 GitHub 直接拒绝 push。

**怎么处理**：把大文件移出 Git（放网盘/对象存储），用 `.gitignore` 排除掉自动生成的大文件夹。已经进历史的大文件清理起来很麻烦，只能用专门工具改写历史。

**学到了什么**：
- 🔑 **Git 是管文本（代码、笔记）的，不是网盘**。大的二进制文件（视频、数据集、安装包）别塞进去。
- `node_modules/`、`dist/` 这类自动生成的，一律 `.gitignore`。
- 👉 对应 [避坑 15](./22-新手避坑指南.md)。

## 案例 12 · 顿悟时刻：原来分支这么轻

**发生了什么**：小钱一开始死活不敢开分支，觉得"复制一整份项目多浪费、多危险"，所有改动都在 main 上小心翼翼地做，特别累。

**怎么处理**：直到他读懂了"**分支只是一个指向某提交的指针，开分支几乎零成本**"（指针模型），整个人通透了。从此他开分支像呼吸一样自然：试个想法开个分支，成了合并、砸了删掉，main 永远干净。开发效率和心情都上了一个台阶。

**学到了什么**：
- 🔑 **理解"分支=轻量指针"，是从"会用 Git"到"敢用、爱用 Git"的分水岭。**
- 很多对 Git 的恐惧，都源于"不懂它内部其实只是在挪指针、加快照"。懂了原理，恐惧自消。
- 👉 对应 [指针模型](./25-必学模型/01-数据模型.md)、[快照-指针框架](./26-思维框架.md)。
