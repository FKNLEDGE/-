## 图 1 · 全景：本地与云端怎么联动

```
        你的电脑（本地，装了 Git）                    GitHub（云端网站）
 ┌───────────────────────────────────────┐    ┌──────────────────────────┐
 │                                       │    │                          │
 │  ①工作区        ②暂存区      ③本地仓库  │    │      ④远程仓库            │
 │  你正编辑      "这次打包"    全部历史    │    │   备份 + 协作中心          │
 │  的文件         的清单       (快照链)   │    │   (默认外号 origin)       │
 │    │             │            │       │    │         │                │
 │    │  git add    │  git commit│       │    │         │                │
 │    ├────────────►│───────────►│       │push│         │                │
 │    │             │            │───────┼───►│ ───────►│                │
 │    │             │            │       │pull│         │                │
 │    │             │            │◄──────┼────┼─────────┤                │
 │                                       │    │         │                │
 └───────────────────────────────────────┘    └─────────┼────────────────┘
                                                         │
                                          队友也能 clone/pull/push 同一个云端仓库
```
> 一句话：**改动从工作区一路 add→commit→push 走到云端；别人的更新 pull 回来。**

## 图 2 · 三区域：一个改动的旅程

```
  写/改文件         git add          git commit          git push
┌──────────┐    ┌──────────┐     ┌──────────┐       ┌──────────┐
│  工作区   │───►│  暂存区   │────►│  本地仓库 │──────►│  GitHub  │
│ (我改了)  │    │ (选这些)  │     │ (存档+留言)│       │ (传上云) │
└──────────┘    └──────────┘     └──────────┘       └──────────┘
  撤销↓           撤销↓             撤销↓               撤销↓
 git restore   restore --staged   reset/amend         revert
```
> 一句话：**东西在哪一层，就用对应那层的命令去操作或撤销。**

## 图 3 · 提交历史：快照串成的链

```
时间 ──────────────────────────────────────────►

 ●─────────●─────────●─────────●  ← main 分支(指针)指着最新这个
 A         B         C         D     ← HEAD 也在这(你站这)
 │         │         │         │
"初始"   "加功能"  "修bug"   "改文档"   每个●都是一张完整快照
 a1b2c3    d4e5f6    7g8h9i    j0k1l2   每个都有唯一哈希身份证
```
> 一句话：**提交不是覆盖，是一张张快照往后串；分支只是指着某张快照的指针。**

## 图 4 · 分支与合并：分出去，再汇回来

```
                  feature 分支(指针)
                       ↓
            ┌───●───────●  E、F：在分支上的提交
            │   E       F
 ●───●───●──┴────────────────●  ← merge：把 E、F 汇回 main
 A   B   C                   M     M 是合并提交(有两个父亲)
                  ↑
              main 分支
              (合并后 main 指到 M)

开分支 = 贴张便利贴(零成本)   合并 = 两条线汇成一个新快照
```
> 一句话：**主线照常，分支里随便试；成了 merge 回来，砸了删掉分支。**

## 图 5 · merge vs rebase：两种"汇合"的区别

```
 ── 起点 ──
        ●───●───●   main
            ╲
             ●───●  feature(你的)

【merge 合并】留下交叉与合并点：      【rebase 变基】把你的提交搬到末端，变直线：
        ●───●───●───────M             ●───●───●───●'──●'
            ╲         ╱                main          (你的提交"假装"从最新点开始)
             ●───●───┘                 历史是一条直路，没有合并点
         历史有分叉痕迹                  ⚠️ 别对已push的提交rebase
```
> 一句话：**merge 保留真实分叉，rebase 让历史变直线更好看；小白先用 merge。**

## 图 6 · 冲突：机器喊你来当裁判

```
两人都改了同一行 → Git 没法决定 → 在文件里摆出"对峙"：

  ┌─────────────────────────────┐
  │ <<<<<<< HEAD   (我方版本)     │  ← 删掉这些标记
  │ 项目状态：稳定                │  ← 我的内容
  │ =======        (分隔线)      │
  │ 项目状态：开发中              │  ← 对方的内容
  │ >>>>>>> feature (对方版本)   │  ← 删掉这些标记
  └─────────────────────────────┘
            │
            ▼  你删掉标记、留下最终内容
  ┌─────────────────────────────┐
  │ 项目状态：开发中（即将稳定）   │ → git add → git commit  ✅完成
  └─────────────────────────────┘
```
> 一句话：**冲突是设计不是故障；你删标记、留想要的、add、commit，裁决完成。**

## 图 7 · 撤销四件套：哪个后悔药治哪种病

```
              改动走到哪一步              用哪个后悔药
  工作区改乱了(没add)  ───────────────►  git restore         (橡皮擦)
  add 了想撤回         ───────────────►  git restore --staged (退出纸箱)
  commit 了(没push)    ───────────────►  reset / commit --amend(挪书签/改上条)
  push 了(已公开)      ───────────────►  git revert           (写更正声明)
  好像彻底删没了       ───────────────►  git reflog           (调监控录像)

  原则：没push的随便改(reset)，已push的用revert(别动公开历史)
```
> 一句话：**Git 极难真正丢东西，对症选后悔药即可。**

## 图 8 · Clone vs Fork：下载 vs 抄一份到自己名下

```
            ┌──────────── GitHub（云端）────────────┐
            │   原作者/项目                          │
            │       │  Fork(云端复制到你名下)         │
            │       ▼                               │
            │   你/项目(副本，你有全权)               │
            └───────┼───────────────────────────────┘
                    │ git clone(下载到本地)
                    ▼
              你的电脑(本地仓库)

  Fork = 云端→云端，抄一份到自己账号    Clone = 云端→本地，下载到电脑
  开源贡献：先 Fork 再 Clone 你的 Fork
```
> 一句话：**Fork 是"抄到自己账号"，Clone 是"下载到电脑"，开源贡献两个都要用。**

## 图 9 · Pull Request：一封"请合并我的改动"的申请

```
  你的分支(改好了)              原仓库 main
       │                          │
       │   发起 Pull Request       │
       ├─────────────────────────►│
       │                          │
   ┌───┴────────────────────────┐ │
   │ PR 页面：                   │ │
   │  • Conversation 总讨论       │ │
   │  • Commits   有哪些提交      │ │
   │  • Files changed 逐行diff+评论│ │ ← 审查在这里发生
   │  • Checks   自动测试✅/❌     │ │
   └───┬────────────────────────┘ │
       │  审查通过 → Merge          │
       └─────────────────────────►● ← 你的改动进了 main
```
> 一句话：**PR 不是代码本身，是"围绕一组改动的讨论+审查+合并"的场所。**

## 图 10 · 一个改动从想法到上线（把全流程串起来）

```
 💡想法/bug
    │ 开 Issue 记录
    ▼
 📋 Issue ──► 🌿开分支 ──► ✍️改+commit ──► ⬆️push ──► 🔀发PR
                                                        │
                                          🤖自动测试 ──┤
                                          👀人工审查 ──┤ (都过✅)
                                                        ▼
                                                   ✅Merge进main
                                                        │
                                     攒够改动 ──► 🏷️打Tag/发Release
                                                        │
                                     (网站类)──► 🚀Actions自动部署上线
```
> 一句话：**Issue 定义做什么 → 分支+PR 把好质量关 → 合并 → 发布/部署。这就是现代软件协作的主干。**
