# 协作与工程模型（模型 15–20）：从"自己用"到"团队/开源/工程化"

> 前两组让你会"一个人用 Git"。这组让你融入**团队、开源社区和工程化**的世界。

---

## 模型 15 · Fork-PR 模型（开源协作的核心）

**是什么**：你对别人的仓库**没有写权限**，但仍想贡献。流程：**Fork**（把它复制一份到你账号下，你对副本有全权）→ 在副本上改 → 发 **Pull Request**（向原作者申请"把我的改动合并进去"）。

**解决什么**：在"开放参与"和"守住底线"之间取得平衡（第一性原理 9）——人人可贡献，但合不合由原作者把关。

**小白怎么理解**：
> 你想给一本开源菜谱改个错。你不能直接在作者的书上涂改，于是**抄一份到自己本子（Fork）**，改好后**把你的修改建议递交给作者（PR）**，作者觉得好就采纳进原书。

```
原作者/项目 ──Fork──► 你/项目(副本,你有全权) ──改──► 发PR──► 原作者审查──► 合并
```

**坑**：
- Fork（云端复制副本）≠ Clone（下载到本地），一次开源贡献两者都要用（先 Fork 再 Clone 你的 Fork）。
- 原作者长期不理 PR 很常见，别往心里去。详见 [第 06 章](../06-团队协作-Fork与PR.md)。

## 模型 16 · 工作流模型（团队的"交通规则"）

**是什么**：团队需要约定"分支怎么开、怎么合、谁能动主线"。常见三种：

| 工作流 | 怎么玩 | 适合 |
| --- | --- | --- |
| **GitHub Flow**（最简单，推荐新手团队） | main 永远可用；每个改动开短分支→PR→审查→合并→删分支 | 大多数中小项目、持续部署 |
| **Git Flow**（较重） | main + develop + feature/release/hotfix 多种长期分支 | 有明确版本发布周期的大项目 |
| **主干开发（Trunk-based）** | 大家都往 main 提交（配强自动化测试），分支极短命 | 成熟团队、强 CI 文化 |

**解决什么**：让多人协作**有序、主线始终可用**（第一性原理 7）。

**小白怎么理解**：像**交通规则**。一个路口没规则就会撞车；约定"靠右行、红灯停"，大家才能高效不乱。工作流就是团队的 Git 交规。

**坑**：
- 别一上来上最复杂的 Git Flow。**小团队/个人用 GitHub Flow 足矣**：开分支→PR→合并，就这么简单。
- 工作流是"约定"，关键是**团队一致**，不是越复杂越高级。

## 模型 17 · 代码审查模型（Code Review）

**是什么**：改动在合并进主线**前**，由别人（或你自己）在 PR 的 "Files changed" 里**逐行查看、提意见**，通过了才合并。

**解决什么**：①**挡住问题**（第二双眼睛能发现 bug、隐患）；②**传承知识**（团队互相学习、统一风格）；③**留痕**（为什么这么改，讨论都记录在 PR 里）。

**小白怎么理解**：像**论文/作业交之前请人帮你看一遍**。审查者把鼠标移到某一行，点 ➕ 就能针对那行留评论："这里变量名能不能更清楚？""这个边界情况考虑了吗？"

**坑**：
- 审查是对**代码**不是对**人**。收到意见别玻璃心，提意见也对事不对人（社区缩写 `nit` = 小建议不强求，`LGTM` = 没问题可合，见 [第 18 章](../18-英文界面与报错直译对照.md)）。
- 改完审查意见，在**同一分支**继续 commit + push，PR 会自动更新，不用重开。

## 模型 18 · Issue / 项目管理模型

**是什么**：GitHub 不只是放代码，还是**协作管理**平台。
- **Issue（议题）**：一个个"要做的事/要修的 bug/要讨论的话题"的帖子。
- **Label（标签）**：给 Issue 分类（`bug`/`enhancement`/`good first issue`…）。
- **Milestone（里程碑）**：一组 Issue 的阶段目标（如"v2.0 发布")。
- **Projects（项目板）**：看板（待办/进行中/已完成），拖卡片管进度。

**解决什么**：把"要做什么、谁在做、做到哪了"**结构化地管起来**，让协作不靠记忆和口头。

**小白怎么理解**：Issue 是**工单/便利贴**，Label 是**给便利贴贴的颜色分类**，Project 是把便利贴排进**看板墙**（待办→在做→完成）。

**坑**：
- 好 Issue 要写清**复现步骤、期望、实际、环境**（见 [第 06 章](../06-团队协作-Fork与PR.md)）。
- PR 里写 `Closes #12`，合并时自动关掉 12 号 Issue——把"做"和"要做的事"联动起来。

## 模型 19 · 自动化模型（CI/CD / Hooks）

**是什么**：让机器在**特定事件发生时自动执行步骤**。
- **GitHub Actions / CI**：push 或提 PR 时，云端自动跑测试、检查、部署（PR 上的 ✅/❌ 就是它）。
- **Git Hooks**：本地的"触发器"，比如提交前自动格式化代码、检查有没有混入密钥。

**解决什么**：把**重复、易忘、易错**的事（跑测试、部署、检查规范）交给机器，**自动守住质量底线**。

**小白怎么理解**：像家里的**自动化规则**——"到家就自动开灯连 WiFi"。这里是"有人 push 就自动跑测试""测试不过就亮红灯不让合并"。

**坑**：
- 配置放固定位置 `.github/workflows/*.yml`，YAML **缩进用空格不用 Tab**。
- 🔐 密钥别写进 yml，用仓库 Secrets。详见 [第 12 章](../12-GitHub-Actions自动化入门.md)。

## 模型 20 · 发布与版本模型（Tag / Release / 语义化版本）

**是什么**：
- **Tag（标签）**：钉在某个提交上的**不动指针**，给"这一刻的版本"起个名，通常是版本号 `v1.2.3`。
- **Release（发布）**：基于 tag 的一个**正式发布**，可附带打包好的成品、更新说明。
- **语义化版本（SemVer）**：`主版本.次版本.修订号`（`MAJOR.MINOR.PATCH`）——破坏性改动升主版本、加功能升次版本、修 bug 升修订号。

**解决什么**：让"哪个是 1.0、哪个是 2.0、它们差在哪、怎么下载成品"**清清楚楚**，方便别人选版本、追更新。

**小白怎么理解**：
> Tag 像给书的某一版**贴上"第 3 版"的封面**；Release 像**正式出版发行**（还附赠装订好的成品）；版本号 `v2.1.3` 一看就知道"大改过 2 次、加过 1 批功能、修过 3 次小错"。

**坑**：
- 普通 commit 是"日常存档"，tag/release 是"郑重其事的版本节点"，别混。
- 看一个项目用得放不放心，去看它的 **Releases** 有没有规律更新（呼应 [第 15 章](../15-看懂和运行别人的项目.md)）。

## 🔗 六个协作工程模型怎么协同

```
       Issue(18 要做什么) ──► 开分支干活 ──► 发 PR
                                              │
                            17 审查 ◄─────────┤
                            19 自动化测试 ◄───┤  (✅才放行)
                                              ▼
                        15 Fork-PR / 16 工作流 决定"怎么合进主线"
                                              ▼
                                          合并进 main
                                              ▼
                            积累到一定程度 ──► 20 打 Tag / 发 Release
```

> 🔑 **一句话总纲**：**Issue 定义要做什么 → 工作流规定怎么做 → PR+审查+自动化把好质量关 → Tag/Release 郑重发布。** 这就是现代软件协作的骨架，而它全长在前两组数据/操作模型的地基上。
