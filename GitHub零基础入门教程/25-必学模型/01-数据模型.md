# 数据模型（模型 1–6）：Git 内部到底长什么样

> 这组是 Git 的"世界观"。**很多让小白迷惑的现象，理解了这 6 个模型就豁然开朗。** 强烈建议把模型 1、2、5 啃透。

每个模型四段读：**是什么 / 解决什么 / 小白怎么理解 / 坑**。

---

## 模型 1 · 快照模型（Snapshot）

**是什么**：每次 `commit`，Git 给你项目当时的**全部文件拍一张完整的照片（快照）**存起来——而不是只存"这次改了哪几行"。（没变的文件，它用指针复用上一张照片里的，所以不浪费空间。）

**解决什么**：让"回到任意一个历史版本"变成**瞬间、完整**的事——因为每个版本本来就是一张完整的照片，直接调出来即可，不用从一堆"差异"里一层层往回算。

**小白怎么理解**：
> 想象你每次提交，都给整个房间**拍一张照片**。要回到上周三的样子？把那张照片调出来照着摆就行。Git 不是记"上周三你挪了把椅子"，而是直接存了"上周三整个房间的样子"。

**坑**：
- ⚠️ 很多教程/老印象说"Git 存的是 diff（差异）"，**这是错的**。Git 存快照，diff 是它**临时算给你看的**。理解这点，后面"为什么切版本那么快""为什么分支那么轻"才说得通。
- 你在 GitHub 上看到的"+/-行变化"是 Git **现场对比两张快照**算出来的展示，不是它存储的形式。

## 模型 2 · 三区域模型（Working / Staging / Repository）

**是什么**：你的一个改动，要经过三个区域才能进历史：**工作区（你正改的文件）→ 暂存区（这次要打包的清单）→ 本地仓库（存档的历史）**。`git add` 把改动从①送到②，`git commit` 从②送到③。

**解决什么**：让你能**精挑细选**——一次改了 10 个文件，可以只把相关的 3 个打包成一个"主题明确"的提交，而不是一锅烩。

**小白怎么理解**：
> 像**寄快递**：工作区=你家里散落要寄的东西；暂存区=你挑进纸箱、准备打包的那些；本地仓库=封箱贴单入库。`add`=挑进纸箱，`commit`=封箱存档。

```
 工作区 ──git add──► 暂存区 ──git commit──► 本地仓库 ──git push──► 远程(GitHub)
 "我改了"           "选这些打包"          "封箱存档"          "寄出去"
```

**坑**：
- ⚠️ 最常见误解："改了文件就等于进 Git 了"。**不是**——不 `add` 不 `commit`，Git 只是"看见"了改动，没有保存。
- `git add` 之后又改了文件？那"又改的部分"还在工作区，没进暂存区，需要再 `add` 一次。

## 模型 3 · 哈希与内容寻址模型（Hash / SHA）

**是什么**：Git 给每一块内容（文件、目录、提交）都算一个**由内容本身决定的唯一指纹**（那串 40 位的 `a1b2c3...`，叫 SHA-1/SHA-256 哈希）。内容相同→指纹相同→只存一份；内容变一个字节→指纹完全不同。

**解决什么**：①**去重省空间**（相同内容只存一次）；②**当身份用**（用指纹精确指代某个版本）；③**防篡改**（改了内容指纹就对不上，立刻露馅）。

**小白怎么理解**：
> 像给每段内容生成一个**专属身份证号，而且这个号是按"长相"算出来的**。整容（改内容）哪怕一点点，身份证号就全变。所以你报一个号，就能精确找到那段内容；别人偷改了，号对不上，造假当场暴露。

**坑**：
- 你**不用记、也不用看懂**那串哈希。需要指代某次提交时，用**前 7 位**就够（`a1b2c3d`），`git log --oneline` 就是只显示前 7 位。
- 它不是"加密"，是"指纹/校验"，目的是唯一标识和完整性，不是保密。

---

## 模型 4 · 提交图模型（DAG，有向无环图）

**是什么**：每个提交都记着"我的上一个提交（父提交）是谁"。一串提交靠"父指针"串起来，分叉、合并之后，整体就成了一张**有向无环图（DAG）**——有方向（指向父辈）、不会绕回自己。

**解决什么**：用一条直线没法表达"同时有好几条开发线、它们还会合并"。图能。它让"分支、合并、历史"有了统一的底层结构。

**小白怎么理解**：
> 像**家谱**：每个人都知道自己父母是谁，顺着往上能追到祖先。提交也一样，顺着父指针往回走就是历史。两个人结婚（合并）就让两支家谱并到一起——这就是 merge。

```
A ← B ← C ← D        (main 主线，箭头指向"父提交")
         ↖
          E ← F      (从 C 分叉出的 feature 分支)
```

**坑**：
- "无环"意味着历史**只能往前加，不能凭空改中间**——这正是 Git 历史可信的根基（呼应模型 3）。
- 合并提交（merge commit）有**两个父亲**（来自被合并的两条线），这是正常的。

## 模型 5 · 引用即指针模型（Branch / HEAD / Tag 都是指针）

**是什么**：**分支不是文件夹的副本**，它只是一个**指向某个提交的、可移动的小指针**（本质就是一个存着提交哈希的小文件）。`HEAD` 是"你现在站在哪"的指针，`tag` 是"钉在某提交上的不动指针"。

**解决什么**：让"开分支"变成**几乎零成本**的操作——不复制任何文件，只是新建一个 41 字节的指针。于是你可以毫无心理负担地开分支做试验。

**小白怎么理解**：
> 分支就像贴在书某一页上的**便利贴**。给书加一张便利贴（开分支）几乎不费事；你写新内容（提交），便利贴就自动往后挪，始终贴在"最新那页"。`HEAD` 是那张写着"我在读这里"的便利贴。

```
        main
         ↓
A ← B ← C
         ↖ feature   ← feature 也只是个指针，指向 C
         
你在 feature 上提交 E 后：
A ← B ← C ← E
             ↖ feature(指向E)、HEAD
         main 还指着 C 没动
```

**坑**：
- ⚠️ 切换分支会让**工作区文件变成那个分支的样子**，会"消失/出现"文件——这不是丢了，是另一个指针指向的快照不同（呼应模型 1）。
- 删分支（`git branch -d`）删的只是**那个指针**，提交本身如果已被合并就还在；理解这点就不会怕删分支了。

## 模型 6 · 分布式仓库模型（Distributed）

**是什么**：和"中心式"不同，Git 让**每个人的电脑上都有一份完整仓库**（含全部历史）。GitHub 上那份并不特殊，只是大家**约定**用来同步的"公共集合点"，默认外号 `origin`。

**解决什么**：①**抗单点故障**（任何一份没了，从别处克隆就全回来）；②**能离线干活**（本地就是完整仓库，commit 不需要网）；③**灵活协作**（可以人对人同步，不一定都经过中心）。

**小白怎么理解**：
> 不是"一个班只有老师有课本，大家轮流借"，而是"**每个同学都有一整本课本**"。GitHub 像班级的**公共书架**，大家把各自的更新放上去同步。谁的书丢了，照着别人的再印一本就行。

```
   你的电脑(完整仓库) ⇄ GitHub(公共同步点) ⇄ 队友的电脑(完整仓库)
        每一份都有全部历史，远程只是"约定的中转站"
```

**坑**：
- ⚠️ "我 commit 了"≠"传到 GitHub 了"。commit 只进**本地**仓库，必须 `push` 才到远程（这是分布式的直接结果，也是模型 8 的内容）。
- 既然各有一份，就可能"我的本地"和"远程"不一致——于是需要同步机制（push/pull）和冲突处理。

---

## 🔗 六个数据模型串起来

```
模型1 快照 ─── 每次提交=一张完整照片
   └ 模型3 哈希 ── 照片和每块内容都有"按内容算的身份证"(去重+防改)
        └ 模型4 提交图 ── 照片靠"父指针"串成家谱(DAG)
             └ 模型5 指针 ── 分支/HEAD/tag 只是指向某张照片的便利贴(所以分支极轻)
模型2 三区域 ─── 改动从 工作区→暂存→本地仓库 逐级流动
模型6 分布式 ─── 这套仓库人手一份，远程只是约定的同步点
```

> 🔑 **一句话总纲**：**Git = 一串用哈希标识、用父指针串成图的"完整快照"，再加上几个指向它们的可移动指针；这套东西人手一份。** 把这句话想透，你比 90% 的使用者更懂 Git。
