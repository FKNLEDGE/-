# 操作模型（模型 7–14）：日常每一步在干什么

> 这组覆盖你 95% 的日常动作。建立在 [数据模型](./01-数据模型.md) 之上——每个操作本质都是"挪指针、加快照、对比快照"。

---

## 模型 7 · 暂存-提交模型（add / commit）

**是什么**：两步走。`git add` 把工作区的改动放进**暂存区**（挑要打包的）；`git commit` 把暂存区的内容**封装成一个提交**（一张快照 + 说明），存进本地仓库。

**解决什么**：把"我改了什么"和"我要把哪些作为一个有意义的整体记录下来"**分开**，让每个提交都主题清晰、可读。

**小白怎么理解**：寄快递的"挑进纸箱（add）→ 封箱贴单（commit）"。

**坑**：
- `git add .` 的点表示"当前目录所有改动"，方便但**可能误加不该传的**（密码、垃圾文件）——commit 前用 `git status` 看一眼。
- 提交信息（`-m "..."`）要说清"做了什么"，别写 `update`。

## 模型 8 · 推拉同步模型（push / pull / fetch）

**是什么**：本地和远程是两份（模型 6），需要同步。
- `git push`：把本地的新提交**上传**到远程。
- `git fetch`：把远程的新提交**下载到本地**，但**不动你当前的文件**（只是"取回来看看"）。
- `git pull`：= `fetch` + `merge`，下载远程更新**并立刻合并**进你当前分支。

**解决什么**：让分布式的多份仓库能对齐。

**小白怎么理解**：
> `push`=把你的更新**上传**到云盘；`fetch`=**只下载**云端最新状态到本地仓库（先不覆盖你正在看的）；`pull`=下载**并直接更新**你眼前的文件。

```
   本地 ── push ──► 远程        (我的更新，传上去)
   本地 ◄── fetch ── 远程        (取回远程状态，但不动我的工作区)
   本地 ◄── pull ─── 远程        (取回 + 直接合并到我眼前)
```

**坑**：
- ⚠️ **干活前先 `pull`**，否则别人更新了你不知道，push 会被拒、还容易冲突。
- `fetch` 更"温和安全"，老手常 `fetch` 后先看差异再决定合不合；`pull` 更省事但有时会触发意外合并。

## 模型 9 · 远程跟踪模型（origin/main 是什么）

**是什么**：本地有个 `main` 分支，还有个带斜杠的 `origin/main`。后者是 Git 在本地保存的**"上次同步时，远程 main 长啥样"的影子**。`git fetch` 会更新这个影子。

**解决什么**：让 Git（和你）能**对比"我本地的 main"和"云端的 main"差多少**，从而知道"我领先几个提交 / 落后几个提交"。

**小白怎么理解**：
> `origin/main` 像你手机里**缓存的"对方最后一次在线状态"**。真人（远程）可能又动了，但你看到的是上次同步的快照。`fetch` 就是刷新这个缓存。

**坑**：
- `git status` 里 "Your branch is ahead of 'origin/main' by 2 commits"=你有 2 个提交没 push；"behind by N"=远程有 N 个你没 pull。看懂这句，你就知道该 push 还是 pull。
- 第一次推新分支要 `git push -u origin 分支名`，`-u` 把本地分支和远程的关联建好，以后直接 `git push`。

## 模型 10 · 分支隔离模型（branch）

**是什么**：分支是指向某提交的可移动指针（模型 5）。在分支上提交，只动这条分支的指针，**别的分支纹丝不动**，于是各条线互不干扰。

**解决什么**：让你**隔离地**做试验/新功能（第一性原理 7）——成了并回去，砸了直接删。

**小白怎么理解**：游戏的"平行存档"。主存档不动，开个分存档随便浪，浪好了再合并主线，浪砸了删掉读主存档。

**坑**：
- 切分支前，最好先 commit 或 stash 当前改动，否则可能挡路（报"please commit or stash"）。
- 分支名要有意义：`fix-login-bug`、`add-search`，别叫 `test1`、`新建分支`。

---

## 模型 11 · 三方合并模型（merge）

**是什么**：合并两条分支时，Git 找到它们的**共同祖先**，再对比"祖先 vs 我方 vs 对方"三者（所以叫三方合并）。各自改了**不同地方**→自动合；改了**同一处**→冲突，交给人（模型 13）。合并通常产生一个有两个父亲的"合并提交"。

**解决什么**：把分头开发的成果汇到一起（第一性原理 5、6）。

**小白怎么理解**：
> 两个人拿着同一份文档的复印件各自批注。合并 = 找到原始那份做基准，把两人**改在不同段落**的批注都并进来；如果两人**改了同一句**，就得喊停问"听谁的"。

**坑**：
- "Fast-forward（快进）合并"：如果主线在你拉分支后没动过，合并就只是把指针往前挪一下，不产生合并提交，这是正常的。
- 合并方向别搞反：先切到"要接收成果"的分支，再 `git merge 带来成果的分支`。

---

## 模型 12 · 变基模型（rebase）

**是什么**：另一种"整合两条线"的方式。`rebase` 把你这条分支的提交**一个个搬到目标分支的最新提交之后**，效果像"假装你一开始就是从最新基点开发的"，历史变成**一条直线**（没有合并提交）。

**解决什么**：让历史更**线性、整洁、好读**——没有一堆交叉的合并提交。

**小白怎么理解**：
> merge 是"两条路在路口**汇合**，留下一个交叉口"；rebase 是"把你走的那段路**整体平移**，接到主路末端，看起来就一条直路"。

```
merge 后:  A─B─C─────M(合并提交)        rebase 后:  A─B─C─E'─F'
                ╲   ╱                                (E、F 被"搬"到 C 后面，变直线)
                 E─F
```

**坑**：
- 🚨 **黄金禁忌：不要对已经 push、别人可能在用的提交做 rebase**（它会重写历史、改哈希，让别人本地错乱）。只在"自己还没公开的本地提交"上用。
- 小白阶段：**先用 merge 就够了**。rebase 等你理解深了再碰，知道"它能把历史弄直、但别碰公开历史"即可。

## 模型 13 · 冲突裁决模型（conflict）

**是什么**：当合并/变基/pull 遇到"双方改了同一处"，Git 停下，在文件里用标记圈出两个版本，让你这个**人类裁判**决定最终内容。

**解决什么**：机器无法判断"两个都对但不同"的取舍，把这个决定权**显式交给人**（第一性原理 6）。

**小白怎么理解**：文件里出现这种"对峙"：
```
<<<<<<< HEAD（我方）
项目状态：稳定
=======
项目状态：开发中
>>>>>>> feature（对方）
```
你删掉三行标记、留下最终想要的内容，再 `add` + `commit`，裁决完成。

**坑**：
- ⚠️ 三行标记（`<<<<`/`====`/`>>>>`）**必须全删干净**，留一个都会变成文件里的垃圾。
- 不确定该留谁的，**去问改了那行的人**，别擅自删别人的工作。想放弃整个合并：`git merge --abort`。
- 详细手把手见 [第 05 章](../05-分支与合并.md)。

## 模型 14 · 撤销/时光机模型（restore / reset / revert / reflog）

**是什么**：因为历史是不可变的快照链（模型 1、4），"回到过去"几乎总能做到。四个工具各管一段：

| 工具 | 管什么 | 一句话 |
| --- | --- | --- |
| `git restore` | 工作区/暂存区 | 丢弃还没提交的改动 |
| `git reset` | 移动分支指针 | 退回到某个提交（改本地历史） |
| `git revert` | 加反向提交 | 安全地抵消某次**已公开**的提交 |
| `git reflog` | 操作日志 | 连"撤销本身"都能找回，终极后悔药 |

**解决什么**：让人**敢操作**（第一性原理 8）——错了几乎都能救。

**小白怎么理解**：
> `restore`=橡皮擦（擦掉没存的草稿）；`reset`=把书签往回挪几页（私下重来）；`revert`=写一页"声明上一页作废"（公开更正，不撕书）；`reflog`=监控录像（连你刚才干了啥都录着，能倒带）。

**坑**：
- 🚨 **没 push 的历史用 `reset` 随便改；已 push 的用 `revert` 来抵消**——别对公开历史 reset/强推（呼应模型 12 的禁忌、第一性原理 8）。
- `git reset --hard` 会丢工作区改动，用前想清楚；真丢了还有 `git reflog` 兜底。
- 详细场景见 [第 07 章](../07-常见问题与撤销操作.md)。

```
        ┌── 7 暂存提交 ──┐         本地仓库
工作区 ──┤               ├── commit ──►  ●─●─●  ──┬── 8 push/pull ──► 远程
        └── (add)        ┘              (DAG)    │
                                        ▲        └── 9 origin/main 跟踪
                            10 分支隔离 │
                            11 merge / 12 rebase 整合分支
                            13 冲突→人裁决
                            14 restore/reset/revert/reflog 后悔药
```
