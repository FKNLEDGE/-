# 07 · 常见问题与撤销操作（你的"后悔药"大全）

> Git 最让人安心的一点：**几乎所有操作都能撤销**。这一章是一本"急救手册"——出错时按症状查，照着抄命令就行。
> 建议第一遍快速扫一眼有哪些"后悔药"，真出事了再回来精读对应那条。

---

## 一、撤销操作：按"改动走到哪一步"对号入座

回忆第 4 章的三个区域。**撤销用哪条命令，取决于你的改动走到了哪一步**。

```
  工作区 ──add──► 暂存区 ──commit──► 本地仓库 ──push──► GitHub
    │①             │②                │③④                │⑤
  还没add        已add未commit     已commit未push      已push到云端
```

### ① 改乱了工作区，想丢弃修改，还原成上次提交的样子

```bash
git restore 文件名          # 丢弃某个文件的改动
git restore .               # 丢弃所有未暂存的改动
```

> ⚠️ 这会**永久丢掉**这些还没保存的修改，无法找回。确认不要了再用。

### ② 已经 `git add` 了，想把文件撤出暂存区（但保留改动）

```bash
git restore --staged 文件名   # 把文件移出暂存区，改动还在工作区
```

> 老命令 `git reset HEAD 文件名` 效果一样。改动本身不会丢，只是退回"未 add"状态。

### ③ 已经 commit 了，但想改最后一次提交（写错了 message，或漏加了文件）

```bash
# 只改提交说明：
git commit --amend -m "正确的提交说明"

# 漏了个文件想补进上一次提交：
git add 漏掉的文件
git commit --amend --no-edit      # --no-edit 表示沿用原说明
```

> ⚠️ `--amend` 是"修改历史"。如果这次提交**还没 push**，随便改；**已经 push 了就别用**（见本章最后"黄金法则"）。

### ④ 已经 commit 了，想彻底撤销最近一次（或几次）提交

**情况 A：想撤销提交，但保留改动的内容**（最常用，给你个"反悔重做"的机会）：

```bash
git reset --soft HEAD~1     # 撤销最近 1 次提交，改动退回暂存区
```

**情况 B：想撤销提交，改动也不要了**（危险，谨慎）：

```bash
git reset --hard HEAD~1     # 撤销最近 1 次提交，改动一并丢弃
```

> `HEAD~1` 表示"最近 1 个提交"，`HEAD~2` 就是最近 2 个，以此类推。
> ⚠️ `--hard` 会**真的删掉**那些改动，用前务必想清楚。

### ⑤ 已经 push 到 GitHub 了，想撤销——用 `git revert`（最安全）

代码已经上云、别人可能已经拉走了，这时**不能"删历史"，而要"用一个新提交来抵消"**：

```bash
git revert <要撤销的提交ID>
```

它会生成一个**新提交**，内容正好是把那次改动反向操作一遍。历史完整保留，对协作最安全。提交 ID 用 `git log --oneline` 查（前面那串 `a1b2c3d`）。

> 🔑 **一句话记牢**：**没 push 的用 `reset` 改历史，已 push 的用 `revert` 加反向提交**。

## 二、高频报错中英对照 + 解法

实际敲命令时最容易撞上的几个错，照下表抄。

### 报错 1：push 被拒绝，提示 `rejected ... fetch first`

```
! [rejected] main -> main (fetch first)
error: failed to push some refs ...
hint: Updates were rejected because the remote contains work that you do not have locally.
```

**啥意思**：GitHub 上有你本地没有的更新（别人推了，或你在网页改过），你本地落后了，不让你直接覆盖。

**解法**：先拉下来合并，再推。

```bash
git pull        # 把云端更新拉下来合并（可能要解决冲突，见第5章）
git push        # 再推
```

### 报错 2：`Authentication failed` / 密码错误

```
remote: Support for password authentication was removed...
fatal: Authentication failed for 'https://github.com/...'
```

**啥意思**：你在用 GitHub **登录密码**推送，但这早就不允许了（见第 2 章）。

**解法**：密码处**粘贴 PAT 令牌**，不是登录密码；或改用 SSH。如果之前存错了凭据，去系统的"凭据管理器/钥匙串"里把旧的 github 条目删掉，下次会重新让你输。

### 报错 3：合并/拉取时 `CONFLICT`（冲突）

```
CONFLICT (content): Merge conflict in xxx
```

**解法**：见第 5 章"合并冲突怎么办"——打开冲突文件，删掉 `<<<<`/`====`/`>>>>` 标记，留下你要的内容，然后 `git add` + `git commit`。想直接放弃这次合并：`git merge --abort`。

### 报错 4：`fatal: not a git repository`

**啥意思**：你在一个**不是 Git 仓库**的文件夹里敲 Git 命令。

**解法**：用 `cd` 进入正确的项目文件夹（里面应有隐藏的 `.git` 文件夹）；或者如果这是个新项目想交给 Git 管，敲 `git init` 初始化。

### 报错 5：命令敲完卡在一个全屏编辑器里出不来（Vim）

**啥意思**：你 `git commit` 没带 `-m`，或者 `git pull` 触发了合并说明，弹出了 Vim 编辑器。

**逃生**：按 `Esc`，再输入 `:wq` 回车（保存退出）或 `:q!` 回车（不保存退出）。
**治本**：commit 记得带 `-m "说明"`。

### 报错 6：中文文件名显示成一串数字 `\344\275\240`

**解法**：让 Git 正常显示中文：

```bash
git config --global core.quotepath false
```

## 三、新手最怕的几个真实场景

### 场景 A：糟糕，我把密码/密钥文件 commit 并 push 上去了！

**这是要紧事**，因为只删文件不够——**它还留在历史记录里，任何人翻历史都能看到**。

**正确处理**：

1. **第一时间作废那个密钥/密码本身**（去对应平台重置、吊销），这是最重要的——假设它已经泄露。
2. 把文件名加进 `.gitignore`，防止再次提交。
3. 从仓库里删除并提交：`git rm --cached 密码文件` → commit → push。这样最新版本不再含它，但**历史里仍有**。
4. 要彻底从历史抹除，需要用 `git filter-repo` 等专门工具改写历史（较进阶），改完强推。但**第 1 步作废密钥永远比擦历史更重要**。

> 🔑 预防永远胜于补救：**push 前用 `git status` 看一眼这次都传了啥**，敏感文件提前写进 `.gitignore`（第 4 章）。

### 场景 B：我想回到三天前那个能正常跑的版本看看

```bash
git log --oneline               # 找到那个版本的 ID，比如 a1b2c3d
git switch -c 回看分支 a1b2c3d   # 基于那个版本开个分支去看，安全不破坏现状
```

看完切回来即可（`git switch main`）。这样既能"回到过去"，又不动你现在的进度。

### 场景 C：我刚才 `git reset --hard` 把东西删没了，能救吗？

**大概率能救！** Git 有个"操作日志"记录你做过的每一步：

```bash
git reflog                      # 列出你所有操作，找到删之前那一步的 ID
git reset --hard <那个ID>       # 跳回去
```

> 💡 `git reflog` 是真正的"终极后悔药"，连"撤销"本身都能撤销。很多看似丢了的提交，靠它都能找回来——所以 Git 里**很难真正永久丢东西**，放宽心大胆用。

### 场景 D：分支名/文件传错了，想改

```bash
git branch -m 旧名 新名         # 重命名当前分支
git mv 旧文件名 新文件名         # 用 Git 的方式重命名/移动文件（会被正确记录）
```

## 四、一条黄金法则（贯穿所有撤销）

> 🌟 **改自己还没 push 的历史，随便（用 reset / amend）；改已经 push、别人可能用到的历史，要克制（用 revert）。**

原因：你一旦 push，别人可能已经基于你的提交在工作了。你偷偷"改历史"再强推，会让所有人的本地仓库错乱。所以**已公开的东西，用"新提交去修正"，而不是"假装它没发生过"**。

唯一例外：你确定这个分支只有你自己用（比如自己的功能分支还没人理会），那 reset 后 `git push --force-with-lease` 强推也行（`--force-with-lease` 比裸 `--force` 安全，会先检查别人有没有推过新东西）。
