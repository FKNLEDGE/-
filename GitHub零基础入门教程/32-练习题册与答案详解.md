## 第一部分 · 概念理解题（检验"懂不懂"）

### 🟢 基础

**1.** Git 和 GitHub 是同一个东西吗？没有网络、不注册账号，能用 Git 吗？

<details><summary>▶ 点击查看答案</summary>

**不是同一个东西。** Git 是**工具**（装在你电脑上的版本控制软件），GitHub 是**网站**（托管 Git 仓库的云平台）。
**没网、不注册也能用 Git**——`add`/`commit`/分支/看历史全在本地，不需要网；只有 `push`/`pull`（和远程同步）才需要网络和账号。
> 类比：Git 是相机，GitHub 是网络相册。考点 → [01 章](./01-Git和GitHub是什么.md)、[第一性原理 3](./24-第一性原理.md)
</details>

**2.** 用一句话说清 `git add` 和 `git commit` 各干了什么，为什么要分成两步？

<details><summary>▶ 点击查看答案</summary>

- `git add`：把改动放进**暂存区**（挑出"这次要打包的"）。
- `git commit`：把暂存区的内容**封装成一个提交**（存档 + 写说明）。
- **分两步的原因**：让你能精挑细选——一次改了 10 个文件，可以只把相关的 3 个打包成一个主题清晰的提交，而不是一锅烩。
> 类比：寄快递的"挑进纸箱(add) → 封箱贴单(commit)"。考点 → [04 章](./04-Git命令行基础.md)、[模型 2/7](./25-必学模型/01-数据模型.md)
</details>

**3.** "我 commit 了"是不是等于"传到 GitHub 了"？

<details><summary>▶ 点击查看答案</summary>

**不等于。** `commit` 只把改动存到**本地仓库**；必须再 `push` 才会上传到 GitHub。
这是分布式模型的直接结果（本地和远程是两份）。所以养成习惯：**收工前 push 一次**，否则换台电脑就拉不到。
> 考点 → [模型 6/8](./25-必学模型/01-数据模型.md)、[避坑 16](./22-新手避坑指南.md)、[案例 7](./30-真实案例库.md)
</details>

### 🟡 进阶

**4.** 为什么说"开一个新分支几乎不花时间、不占空间"？Git 内部其实做了什么？

<details><summary>▶ 点击查看答案</summary>

因为**分支只是一个"指向某个提交的可移动指针"**（本质是个存着提交哈希的小文件，约 41 字节），**不是复制整个项目文件夹**。
开分支 = 新建一个指针指向当前提交，几乎零成本。这就是为什么可以放心大胆地开分支做试验。
> 类比：贴一张便利贴。考点 → [模型 5/10](./25-必学模型/01-数据模型.md)、[思维框架 2](./26-思维框架.md)、[案例 12](./30-真实案例库.md)
</details>

**5.** "Git 存的是快照，不是差异（diff）"——那你在 GitHub 上看到的绿色 `+` / 红色 `-` 行变化是怎么来的？

<details><summary>▶ 点击查看答案</summary>

Git **每次提交存的是当时全部文件的完整快照**（没变的文件用指针复用，不浪费空间）。
你看到的 +/- 行变化，是 Git **现场对比两张快照、临时算出来给你看的**展示，不是它存储的形式。
理解这点，才说得通"为什么切换版本/分支那么快"——直接调出那张完整快照即可，不用从一堆差异里层层往回算。
> 考点 → [模型 1](./25-必学模型/01-数据模型.md)、[第一性原理 1](./24-第一性原理.md)
</details>

**6.** 提交前面那串 `a1b2c3d...`（哈希）是怎么来的？它为什么能防止别人偷改历史？

<details><summary>▶ 点击查看答案</summary>

它是 Git 用**提交内容本身算出来的唯一指纹**（哈希）。内容相同→指纹相同；内容变一个字节→指纹完全不同。
因为指纹由内容决定，**任何人偷改了历史里的一个字，重新算出的指纹就和记录对不上，立刻暴露**。所以 Git 天然防篡改、保证完整性。
你不用记它，指代某次提交用前 7 位即可。
> 考点 → [模型 3](./25-必学模型/01-数据模型.md)、[第一性原理 2](./24-第一性原理.md)
</details>

**7.** `merge` 和 `rebase` 都能整合两条分支，本质区别是什么？rebase 最大的禁忌是什么？

<details><summary>▶ 点击查看答案</summary>

- **merge**：两条线在交汇处生成一个"合并提交"（有两个父亲），**保留真实的分叉痕迹**，历史有交叉。
- **rebase**：把你分支的提交**一个个搬到目标分支末端**，效果像"假装你从最新点才开始开发"，**历史变成一条直线**，更整洁。
- **最大禁忌**：🚨 **不要对已经 push、别人可能在用的提交做 rebase**——它会重写历史、改哈希，让别人的本地仓库错乱。只在自己还没公开的本地提交上用。小白阶段先用 merge 就够。
> 考点 → [模型 11/12](./25-必学模型/02-操作模型.md)、[图解图 5](./28-概念图解大全.md)
</details>

### 🔴 综合

**8.** 用"第一性原理"解释：为什么 Git 要设计成"分布式"（人手一份完整仓库），而不是只放一个中心服务器？这带来了哪两个直接好处？

<details><summary>▶ 点击查看答案</summary>

**根本事实**：任何"唯一的一份"都是脆弱的——电脑会坏、服务器会宕、网络会断。把所有历史只放一个地方就是在赌它永不出事。
**于是设计成分布式**：每个参与者电脑上都有一份完整仓库（含全部历史），GitHub 那份只是"约定的同步点"。
**两个直接好处**：① **抗单点故障**（任何一份没了，从别处克隆就全回来）；② **能离线干活**（本地就是完整仓库，commit 不需要网）。
> 考点 → [第一性原理 3](./24-第一性原理.md)、[模型 6](./25-必学模型/01-数据模型.md)
</details>

## 第二部分 · 操作题（检验"会不会做"）

> 给你一个场景，说出该用什么命令 / 点哪里。

### 🟢 基础

**9.** 你想把 GitHub 上的仓库 `https://github.com/me/notes.git` 下载到本地。命令是？

<details><summary>▶ 点击查看答案</summary>

```bash
git clone https://github.com/me/notes.git
```
下载完会生成一个 `notes` 文件夹，用 `cd notes` 进去。
> 考点 → [04 章](./04-Git命令行基础.md)
</details>

**10.** 你改完了几个文件，想把**全部改动**保存并上传到 GitHub。按顺序写出命令。

<details><summary>▶ 点击查看答案</summary>

```bash
git add .                    # 把所有改动放进暂存区
git commit -m "说明做了什么"   # 存档 + 留言
git push                     # 上传到 GitHub
```
口诀：**加、提、推**（协作时前面还要先 `git pull`）。
> 考点 → [04 章](./04-Git命令行基础.md)、[速查表](./08-命令速查表与术语表.md)
</details>

**11.**（网页操作）你想在 GitHub 网页上新建一个仓库并让它"不为空"，建仓库表单里**必须勾选哪一项**？

<details><summary>▶ 点击查看答案</summary>

勾选 **"Add a README file"**。勾上它会自动生成一个 README.md，仓库才不是空的，后续才好直接在网页编辑/克隆。
> 考点 → [03 章](./03-第一个仓库（网页版）.md)、[17 章](./17-保姆级实操-从注册到第一次提交.md)、[图文卡片 1](./29-图文步骤卡片.md)
</details>

### 🟡 进阶

**12.** 你要开发一个新功能"搜索框"，不想影响主线。写出"新建并切换到分支 → 提交 → 推送该分支"的命令。

<details><summary>▶ 点击查看答案</summary>

```bash
git switch -c add-search       # 新建并切换到 add-search 分支
# ……改代码……
git add .
git commit -m "新增搜索框功能"
git push -u origin add-search  # 首次推送该分支，-u 建立关联
```
之后到 GitHub 发起 Pull Request 请求合并。
> 考点 → [05 章](./05-分支与合并.md)、[模型 10](./25-必学模型/02-操作模型.md)
</details>

**13.** 你想忽略所有 `.log` 文件和整个 `node_modules/` 文件夹，不让它们进 Git。怎么做？

<details><summary>▶ 点击查看答案</summary>

在仓库根目录建一个 `.gitignore` 文件，写入：
```gitignore
*.log
node_modules/
```
一行一个。写进去的文件 `git status` 会当它们不存在，`git add .` 也不会加它们。
⚠️ 注意：`.gitignore` 只能拦"还没被跟踪过"的文件；已经提交过的需额外处理。
> 考点 → [04 章六](./04-Git命令行基础.md)、[gitignore 模板库](./31-延伸资源精选-站在巨人肩上.md)
</details>

**14.**（开源场景）你想给一个**没有写权限**的开源项目贡献代码。按顺序列出关键步骤。

<details><summary>▶ 点击查看答案</summary>

1. **Fork** 原仓库到自己账号（网页点 Fork）。
2. `git clone` 你的 Fork 到本地。
3. `git switch -c fix-xxx` 开分支。
4. 改代码 → `git add .` → `git commit -m "..."`。
5. `git push -u origin fix-xxx` 推到你的 Fork。
6. 到 GitHub 发起 **Pull Request**（base 选原仓库）。
7. 配合维护者审查、修改，直到被合并。
> 考点 → [06 章](./06-团队协作-Fork与PR.md)、[模型 15](./25-必学模型/03-协作工程模型.md)、[专题 9](./27-专题实战/03-团队协作与开源.md)
</details>

## 第三部分 · 排错题（检验"出错能不能救"）

> 给你一个报错或糟糕情况，说出原因和正确处理。

### 🟢 基础

**15.** 你敲命令报 `$: command not found`，最可能是什么原因？

<details><summary>▶ 点击查看答案</summary>

你把教程命令前面的 **`$` 提示符也敲进去了**。`$` 是终端自动显示的，不是命令的一部分。
比如教程写 `$ git status`，你只该敲 `git status`。
> 考点 → [00 章](./00-命令行与终端零基础扫盲.md)、[16 章](./16-命令里的符号与黑话速查.md)、[避坑 4](./22-新手避坑指南.md)
</details>

**16.** `git commit` 后，屏幕突然变成一个奇怪的全屏编辑器，打字也不对、退不出来。怎么逃出来？为什么会这样？

<details><summary>▶ 点击查看答案</summary>

**原因**：commit 没带 `-m "说明"`，Git 弹出了 Vim 编辑器让你写提交信息。
**逃生**：按 `Esc`，输入 `:q!`，回车。
**治本**：以后 commit 记得带 `-m "说明"`。
> 考点 → [04 章](./04-Git命令行基础.md)、[避坑 6](./22-新手避坑指南.md)、[英文报错对照](./18-英文界面与报错直译对照.md)
</details>

### 🟡 进阶

**17.** 你 push 时报 `Updates were rejected because the remote contains work that you do not have locally`。这是什么意思？正确处理是什么？**绝对不要做什么？**

<details><summary>▶ 点击查看答案</summary>

**意思**：远程有你本地没有的更新（别人推了，或你在网页改过），你本地落后了，不让你直接覆盖。
**正确处理**：
```bash
git pull        # 先拉下远程更新并合并（可能要解决冲突）
git push        # 再推
```
**绝对不要**：🚨 用 `git push --force` 强推！那会**覆盖掉别人的提交**，是协作大忌。
> 考点 → [07 章报错 1](./07-常见问题与撤销操作.md)、[18 章](./18-英文界面与报错直译对照.md)、[案例 3](./30-真实案例库.md)
</details>

**18.** 一次提交**已经 push 到 GitHub** 了，现在要撤销它。应该用 `reset` 还是 `revert`？为什么？

<details><summary>▶ 点击查看答案</summary>

用 **`git revert <提交ID>`**。
**原因**：代码已经公开，别人可能已经基于它工作了。`revert` 会**生成一个新提交来抵消**那次改动，历史完整保留，对协作安全。
而 `reset` 是"改写历史"，只适合**还没 push 的本地提交**——对已公开的历史 reset + 强推会让所有人错乱。
口诀：**没 push 用 reset，已 push 用 revert。**
> 考点 → [07 章](./07-常见问题与撤销操作.md)、[模型 14](./25-必学模型/02-操作模型.md)、[第一性原理 8](./24-第一性原理.md)
</details>

### 🔴 综合

**19.** 🚨 你不小心把含数据库密码的 `config.py` 提交并 push 到了**公开**仓库。按优先级列出你的处理步骤。

<details><summary>▶ 点击查看答案</summary>

1. **第一时间去把那个数据库密码作废/重置**（当它已经泄露——确实泄露了，有机器人专扫 GitHub）。**这是最重要的一步。**
2. 把 `config.py` 写进 `.gitignore`，防止再次提交。
3. `git rm --cached config.py` 后 commit + push，让最新版不再含它。
4. （进阶）要彻底从历史抹除需用 `git filter-repo` 等工具改写历史——但**作废密钥永远比擦历史更重要**。
**记住**：删文件没用，它还在历史里；作废密钥才真正解除风险。
> 考点 → [07 章](./07-常见问题与撤销操作.md)、[避坑 1](./22-新手避坑指南.md)、[案例 1](./30-真实案例库.md)
</details>

**20.** 你执行了 `git reset --hard` 后后悔了，提交好像"没了"。还能救吗？怎么救？

<details><summary>▶ 点击查看答案</summary>

**大概率能救**（只要那些提交曾经 commit 过）。
```bash
git reflog                  # 列出你所有操作记录，找到 reset 之前那一步的哈希
git reset --hard <那个哈希>  # 跳回去
```
`git reflog` 是"终极后悔药"，记录了你的每一步操作，连"撤销"本身都能撤销。
⚠️ 但"从未 commit 过"的改动救不回——所以平时要**多 commit**。
> 考点 → [07 章场景 C](./07-常见问题与撤销操作.md)、[模型 14](./25-必学模型/02-操作模型.md)、[案例 2](./30-真实案例库.md)
</details>

## 第四部分 · 综合场景题（检验"能不能用"）

> 没有标准答案，重在思路。先自己写方案，再对照参考。

**21.** 你和两个同学要合作做一个网站，怎么用 GitHub 组织协作？请设计一套工作流程（谁建库、怎么分工、怎么避免互相覆盖、怎么保证主线可用）。

<details><summary>▶ 点击查看参考思路</summary>

1. **一人建仓库**，Settings → Collaborators 把另两人加进来。
2. **约定用 GitHub Flow**：🔑 谁都不直接推 `main`，所有改动走分支 + PR。
3. **分工开分支**：各做各的功能分支（`feature/homepage`、`feature/about`），并行互不干扰。
4. **干活前先 `git pull`**，基于最新开发，减少冲突。
5. 改完发 **Pull Request**，**互相 Review** 后再合并。
6. 合并后各自 `git switch main` + `git pull` 同步最新。
7. 用 **Issues** 拆任务分配，用 **Projects 看板** 看进度。
**为什么这样**：分支隔离护住主线随时可用，PR + 审查把好质量关，先 pull 减少冲突。
> 考点 → [模型 16/17](./25-必学模型/03-协作工程模型.md)、[思维框架 5/6](./26-思维框架.md)、[专题 8](./27-专题实战/03-团队协作与开源.md)、[案例 4](./30-真实案例库.md)
</details>

**22.** 你是研究生，要写毕业论文，还要投不同期刊（格式要求不同）。怎么用 Git/GitHub 管理？

<details><summary>▶ 点击查看参考思路</summary>

1. 建 **Private** 仓库（论文不公开），用 Markdown 写（diff 清晰）。
2. 按章节组织文件夹，README 写题目/进度/待办。
3. **每写一段就 commit**，提交信息当改稿日志（`完成方法部分初稿`、`按导师第3轮意见修改`）。
4. **主线 main 放"标准版"**；投不同期刊时**各开一个分支**（`投稿-期刊A`、`投稿-期刊B`）适配各自格式，互不干扰。
5. 导师返回修改后提交一版，用 diff 一眼看出改了哪里。
6. 大图表/数据用 `.gitignore` 排除，别撑大仓库。
**收获**：多版本管理 + 改稿全程可追溯 + 云端备份永不丢。
> 考点 → [专题 1](./27-专题实战/01-写作与知识管理.md)、[模型 10](./25-必学模型/02-操作模型.md)、[避坑 15](./22-新手避坑指南.md)
</details>

**23.** 用 [思维框架 3「可逆性优先」](./26-思维框架.md) 分析：执行 `git reset --hard HEAD~3` 前，你应该问自己哪三个问题？

<details><summary>▶ 点击查看参考思路</summary>

操作前"可逆性三连问"：
1. **这步可逆吗？** —— `reset --hard` 会丢工作区改动，已 commit 的能靠 reflog 找回，但**没 commit 的会真没了**。
2. **如果错了用什么撤？** —— `git reflog` 找回提交；但未提交的改动无解，所以先确认有没有没保存的东西。
3. **它会影响别人吗？** —— 如果这几个提交**已经 push 且别人在用**，reset + 强推会害了别人，应改用 `revert`。
结论：先 `git status` 确认有无未提交改动，必要时先 commit/stash；若涉及公开历史，改用 revert。
> 考点 → [思维框架 3](./26-思维框架.md)、[模型 14](./25-必学模型/02-操作模型.md)
</details>

## ✅ 怎么用好这套题

1. **先做后看**：每题忍住，先自己想/动手，再展开答案。直接看答案 ≈ 没练。
2. **错题溯源**：答错就去对应章节重读，并**动手操作一遍**。
3. **间隔重复**：今天做一遍，3 天后、1 周后各再做一遍，记忆才牢。
4. **造自己的题**：学完后试着给别人出题、讲解——能讲明白才是真懂。
